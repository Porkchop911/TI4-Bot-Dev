# Decision UI consistency plan

## Goal and current baseline

Make `/dev/decisions` a useful visual and interaction specification for the real game UI: a player should immediately understand **what is being decided, what is available, what is staged, and what submitting will do**. This is a UI work plan, not a claim that the gallery's synthetic choices are reachable engine states.

Today `web/src/dev/decisionGalleryCases.ts` has one illustrative choice for each of 16 `ChoiceWorkflowKind` values, but `DecisionGallery.tsx` passes a placeholder board, no `boardView` or `players`, and no `PlayerIdentityProvider`. Thus the map, resource limits, and “Unknown participant” in previews do not represent the actual game. `choiceModel.ts` classifies invasion separately but `GameShell.tsx` falls back to the generic modal; activation and scoring also use the generic modal. `PendingChoiceModal.tsx` already has a strategy-card layout, but the gallery offers `leadership`/`politics` instead of corpus IDs such as `pok1leadership`/`pok3politics`, so it cannot display the catalog's printed text. Dedicated dialogs, the generic modal, and the wrapped drawers each implement their own headers, borders, close/minimize controls, and footers. Combat's casualty UI assumes one offered option equals one available unit and that all remaining hits can be allocated in the current decision; neither assumption is generally safe (see `combat.rs`'s deduplicated per-type/damage options and sequential hit resolution).

## Shared interaction and design contract

- **One decision frame:** Use one reusable decision surface (dialog or compact board-side panel when spatial context matters) with a neutral border, shared padding, width, typography, scroll area, error slot, and footer. Reserve color for meaningful states: selected/targetable = accent, fulfilled = success, error/destruction = danger. Do not encode workflow identity in a blue/green/purple/red frame border. Keep faction/player colors on map ownership only; show focus and selection with more than color.
- **One header:** Human-readable task title, short instruction from the current choice, optional progress (`2 / 4 hits`, `3 / 5 resources`), and a single icon-only **minimize** button (`−`, accessible name `Minimize decision`, tooltip). No `Inspect Game —`, `Inspect Map —`, or `✕` that actually minimizes. Minimizing never declines/submits. Escape uses the same behavior; a small persistent decision banner offers **Resume decision**. New nonce resets only appropriate draft state and reopens the decision. Show the actor's real nickname/seat only when known; no “Unknown participant” in the actor's own decision header.
- **Plain language:** Prefer “Land ground forces on Jord”, “Assign a casualty”, “Spend influence to vote”, “Propose a trade”, “Choose a strategy card”. Do not expose `Preview: tactical invasion`, `Context: commit_ground_forces`, raw workflow keys, or `Decision Required • Unknown participant` in player-facing dialogs. Keep subtype, IDs, source, nonce, and classification in a clearly marked **gallery/debug details** panel, not the decision itself. Do not claim a numbered stage unless the decision context establishes it (combat is not always space combat, and voting can be a tiebreak).
- **One control vocabulary:** Use a shared row with name, contextual detail, `selected / available` and `−  count  +` for repeatable identical actions; disable at zero, actual max, or a shared budget. Show **Reset selection** when there is a staged basket. Use an on/off planet control for one-time planet exhaustion (a checked card or checkbox; `0 / 1` is optional), not a fake numeric slider. Use a radio/card list for exclusive choices and distinct buttons for immediate accept/refuse/pass. Footer consistently orders Reset (when relevant), optional Finish/Pass (only when explicitly offered), then a specific Confirm action. Never add a meaningless stepper to a single choice.
- **Separate drafts from server state:** Every row and summary distinguishes committed progress from staged changes; display real min/max only when supplied or safely derivable from the authoritative board plus offered choices. Recompute limits after each newer nonce. Do not use option count as unit stock, an illustrative `10` trade-good limit, or `1` hit as a silent fallback. If a bound is unknown, say so and permit only what the current offered choice proves. Disable impossible confirmations without hiding the exact offered finish. For multi-action baskets, explain that confirming submits **one decision at a time** and stops if a subsequent offer differs or is rejected.
- **Spatial decisions get the board:** A usable galaxy view must come from the same `BoardView`, map tiles, seating order, and viewer seat as the choice. Activation: emphasize only offered systems and show target inspection/confirmation. Movement/retreat: show origin/destination. Cargo, invasion, production/placement: show active system and planet/units. Payment and agenda planet voting: provide a _payment view_ of the map with only the actor's ready, offered planets selectable, resource/influence value visible, other planets muted for context, and staged/committed states distinct. Trade goods stay in the side panel. If data is absent, show an explicit limited preview; do not render an invented galaxy or treat an unoffered planet as clickable. On small screens keep map inspection and the minimized banner accessible.
- **One safe submit path:** UI stages selections locally, submits an **offered, unchanged** option ID, and reports errors visibly. Network acceptance is not proof of a new choice: the game client waits for the authoritative newer state/nonce. An interrupted sequential pipeline must stop and show what was committed versus what remains, never silently continue or pretend an all-at-once payload was sent. Retain keyboard operation, focus restoration, accessible names, and private-choice redaction for other seats.

## Gallery and submission inspection

1. Replace the illustrative board placeholder with small, deterministic **synthetic but internally consistent** `BoardView`/map tiles, `PlayerView`, seating order, and a synthetic roster in `PlayerIdentityProvider`. Use separate fixtures for spatial states (activation, ready/exhausted planet payment, invasion, retreat), distinct actors, and enough repeated units/options to exercise steppers. Cross-check example shapes against engine producers (`draft.rs`, `invasion.rs`, `combat.rs`, `vote.rs`, `transactions.rs`, payment/production producers); label every example “synthetic”. Keep deliberate malformed cases in the fallback section. Do not claim 16 workflow examples cover every engine subtype.
2. Put controls for selecting the scenario and simulated rejection outside/above the modal (also reachable when the decision is open via gallery layout). Keep diagnostics in a collapsible developer panel: workflow, subtype, raw prompt, offered IDs, context/constraints, fixture source and viewer mode. A selectable gallery case should have a short player-facing prompt instead of `Preview: <snake_case>`.
3. On **each local submit call**, append a chronological trace: attempted option ID, offered-choice nonce, illustrative game ID/version, the **exact `submit_choice` wire shape** (`type`, `protocol_version`, `game_id`, `nonce`, `expected_version`, `option_id`), and result (`locally recorded` or `simulated rejection`). Clearly label game ID/version as gallery placeholders, never as live server state. Show current locally staged basket separately from the actual next message; for pipelines display the intended sequence as a preview, with future IDs marked _unverified until the next authoritative offer_. Add Copy JSON for the single attempted message; no sessions, secrets, or server connection.
4. A gallery mock must not advance a pending choice just because a callback resolved. For a **multi-step** demo, supply an explicit synthetic next-choice/nonce/version sequence per scenario, or stop after the first submission and show “Awaiting next decision” with remaining intent unconfirmed. Show failures and retry against the currently offered choice. Keep the gallery dev-only as it is now.

## Implementation slices and acceptance checks

1. **Gallery fidelity and diagnostics:** Fixture roster/map/players, corrected prompts and strategy corpus IDs, dev panel, submission trace. Check `DecisionGallery.test.tsx` and `web/e2e/decision_gallery.spec.ts` for a ready-versus-exhausted payment map, absence of “Unknown participant”, strategy printed texts, a copied `submit_choice` with matching offered ID, and failed versus recorded traces. Assert the production bundle still excludes the gallery.
2. **Shared frame and language:** Introduce shared header/minimize/resume/error/footer pieces and design tokens in `web/src/index.css`; migrate generic, wrapped trays, and dedicated combat/agenda/trade/production dialogs in manageable batches. Remove workflow-colored frame borders and nested double headers; standardize icon/ARIA/tooltip and narrow-screen focus. Review one screenshot per workflow at desktop and mobile widths, and keyboard Escape/minimize/resume. Preserve the existing privacy boundary in `GameShell`.
3. **Spatial workflows:** Wire real `BoardView`/viewer data into the decision experience; add activation, invasion and payment-map presentations, then agenda/retreat/placement map variants. Reuse `boardPresentation.ts` target derivation but scope clickable targets to **offered** IDs and verify owned + ready planets using board projection. Test map selection and inspector selection against the same offered option without double submitting; validate missing-board and other-seat views.
4. **Counters and casualty correctness:** Extract a reusable staged-quantity row/tally/reset pattern; apply only to meaningful repeatable actions. First create engine-shaped casualty fixtures showing deduplicated options, damaged and undamaged units, successive nonces and hit depletion. Fix one-hit direct submission before enabling any batch allocation. Add invasion, agenda-vote and transaction draft controls with corresponding offer-by-offer tests; verify pipeline interruption, unexpected offers, and visible partial completion. Keep engine legality and payment mathematics on the server.
5. **Regression gate:** Focused Vitest per migrated component and presentation model, then `npm test`, TypeScript check and production build from `web/`; run gallery Playwright plus selective real-server browser tests for activation/payment/invasion when reachable. Verify actual server progress from a newer authoritative snapshot, never from a gallery callback or an `action_accepted` alone. Track each subtype as a sourced fixture, an explicitly synthetic example, or an open coverage item.

### Done when

Every listed workflow has the shared header/minimize/resume/error experience and its table-defined controls; numeric limits and map targets reflect offered legal choices; casualty assignment works for the engine's per-hit choice shape; strategy cards show the correct corpus text; and the dev route makes both the staged draft and each exact mock outbound message understandable without implying a server transition.
