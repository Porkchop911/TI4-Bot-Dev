# The policy cannot see which system it is activating

Date 2026-08-17. Tool: `cargo run -p ti4-training --example separability --release`.
Pure learning throughout — positions generated by the learned champion playing itself, no
authored policy anywhere in the loop, no teacher, no training.

---

## The test

If two options of a choice carry **identical feature vectors**, no weight vector can prefer one to
the other. Not "this optimiser did not find it" — *no function of these features can*, because the
features do not distinguish the options. The policy is pinned to a coin flip between them for the
rest of time, whatever the learning rule, the reward, or the run length.

That makes the tied fraction a lower bound on the plateau that is independent of everything else,
and it needs nothing but the features themselves to measure.

## The result

40 games, 40,947 decisions:

| head | decisions | blind | tied options | ceiling | distinct slots |
|---|---|---|---|---|---|
| **`activation`** | 2,000 | **94.0%** | **46.1%** | **0.681** | **4.4** |
| `other` | 314 | 29.0% | 18.2% | 0.897 | 12.9 |
| `trade` | 8,004 | 19.0% | 22.4% | 0.954 | 25.8 |
| `combat` | 390 | 11.0% | 16.2% | 0.930 | 25.0 |
| `production` | 2,229 | 1.6% | 0.4% | 0.995 | 27.7 |
| `turn` | 8,709 | 0.0% | 0.0% | 1.000 | 32.0 |
| `secondary` | 3,516 | 0.0% | 0.0% | 1.000 | 36.9 |
| `landing` | 1,929 | 0.0% | 0.0% | 1.000 | 62.6 |
| *(all others)* | | 0.0% | 0.0% | 1.000 | 20–60 |
| **pooled** | **40,947** | **8.7%** | 17.7% | 0.974 | |

The pooled 8.7% understates it badly. The blindness is concentrated in the head with **32 options
per decision**, which generates **44.5% of every option the policy ever scores**, and which decides
the single most consequential thing in a turn: which system to activate.

**`ceiling` 0.681** means that even against a perfect teacher, and with unlimited training, the best
any weight vector could do on activation is 68% — the rest is forced guessing.

## What two indistinguishable options actually look like

Systems **107** and **74**, in a 35-option activation choice. Both carry exactly these ten
features, and nothing else:

```
prompt-kind:activate:activate    = 1     option:activate                = 1
prompt-kind:system:activate      = 1     prompt-option:a:activate       = 1
prompt-kind:a:activate           = 1     prompt-option:system:activate  = 1
                                         prompt-option:activate:activate = 1
target:planet-count              = 2
target:not-controlled-count      = 2
target:uncontrolled-count        = 2
```

Seven of the ten are the word "activate" crossed with the prompt — identical for every option by
construction. The decision rests on **three planet counts**. Two different tiles on the board with
the same counts are, to this policy, the same move.

## Why: two mechanisms, both in `features.rs`

**1. The system's identity is filtered out.** Option tokens drop anything all-digit:

```rust
.filter(|token| !token.chars().all(|character| character.is_ascii_digit()))
```

System ids *are* numeric — `107`, `74`, `18`. So `option:107` and `option:74` never exist, and the
only surviving token is `activate`, from the label. The filter is defensible in general (it stops
the policy memorising specific ids, which would overfit a map), but for activation it removes the
only thing naming the target.

**2. Zero-valued facts are dropped, not recorded as zero.** `add_parts` returns early on `0.0`, so
`target:own-ships = 0` is absent rather than present-and-zero. "No ships here" and "this fact does
not apply" become the same thing, and the absence is what makes two empty systems collide. In the
example above, every unit and reachability feature vanished this way.

## What this does and does not settle

It **does** settle that the plateau has a hard representational component that no optimiser can
touch: 94% of activation decisions are unlearnable as posed. Changing the learning rule, the
reward or the run length cannot move them.

It **does not** show that the other heads are fine. Separability is necessary, not sufficient:
`secondary` is 0% blind with 36.9 distinct slots yet the behaviour-cloning run could not fit it
above chance, so its options differ without differing *usefully*. Those are different problems with
different fixes.

## The fix, and the line it must not cross

`features.rs` opens by insisting that everything in it is an **observation, never a judgement** —
a fact a rule could check, with no opinion about whether it is good. That line is what keeps the
policy fully learned, and the fix stays behind it. What activation needs is more *facts about the
target*, not an opinion about which target is better:

- distance from the player's nearest ship, and from their home system
- distance to Mecatol Rex
- total resources and total influence of the system's planets
- whether it holds a wormhole, and which anomaly kinds
- how many *other* players hold units or control planets there
- planet traits and technology specialties present

None of those is a heuristic; each is something the board states plainly. Any two of them would
separate 107 from 74.

Alongside, the zero-drop needs revisiting for this fixed schema of facts: a count of zero is
information, and dropping it is what turned ten features into three.

## Priority

This is the first hypothesis in the whole plateau investigation that is *proved* rather than
argued, and it sits on the highest-branching head in the game. It should be fixed before any
optimiser work — PPO on a policy that cannot see its own board would converge faster to the same
ceiling.
