## General impressions

This is a large, disciplined body of work with a consistent through-line: **make the Rust
decision surface token-identical to the Python oracle**, then use the freed-up signal to attack
the Stage-2 learning plateau. The engineering quality is high in the places that matter most:

- **The comments are unusually good.** Nearly every change explains the rule it implements, the
  oracle line it was ported from, and — critically — *what broke before*. `py_round_half_even`
  and its "a half-away-from-zero port would price a Trade Agreement at 3 where the oracle asks 2"
  note is the model of what a comment should do.
- **The tests are behavioural, not structural.** The `Recording`/`CommitRecording`/`SpeakerRecording`
  deciders that capture the exact `(prompt, id, kind, label)` tuples are the right instrument for
  a parity project, and asserting on the whole offered surface (not just the chosen answer) is
  what makes the parity claims credible.
- **The experiment flags are honestly defaulted.** `high_vp_bonus`, `clearance_weight`,
  `pipeline`, `rollout_depth`, `panel_step` all default to the reference behaviour, and each
  carries a doc comment saying so. The `--pipeline` / `--rollout-depth` mutual-exclusion check is
  a nice touch.
- **The Stage-2 gate rewrite is a genuine conceptual fix.** Replacing the aggregate cross-faction
  sum with per-faction own-merit pairing removes a real confound (one head carrying or blocking
  another), and the two-path VP/clearance verdict with explicit per-clause failure text is a big
  improvement in diagnosability.

The main weakness is the opposite of the strength: the **faction-as-player-identity migration
was applied thoroughly inside the engine and the training rollout path, but not swept across
every consumer of the engine.** One consumer (`ti4-sim`) silently lost an entire subsystem. That
is exactly the failure mode this project's own smoke test was built to catch, and the smoke test
did not catch it — it was instead widened from 8 to 32 seeds to keep passing.

Second-order theme: several changes are guarded by string comparisons against content-derived or
human-readable text (`name == "Leadership"`, `faction.as_str() != "generic"`,
`detail.starts_with("VP")`). Each is individually defensible; together they are a pattern worth
pushing back on.

## Findings

Ordered by severity.

### F1 — **`ti4-sim` lost the entire promissory-note subsystem** (high, confirmed at runtime)

`promissory::note_id` now keys notes by **faction name** instead of `PlayerId`
(`crates/ti4-engine/src/promissory.rs:66`). But `setup::start_game_seeded` still calls
`promissory::deal` at `crates/ti4-engine/src/setup.rs:128` — *before any faction is seated*, when
every seat's faction is the default `"generic"` (`ti4-model/src/state.rs:400`). Every seat
therefore mints the *same* four keys, and the `BTreeMap` insert makes the last seat shadow all
the others.

The training path noticed and re-deals after seating (`ti4-training/src/rollout.rs:280`, comment
"G1 (T6b)"). **`ti4-sim/src/run.rs::seat()` (line 140) assigns factions and never re-deals.** So
does `ti4-sim/examples/prompts.rs:30` and `examples/objectives.rs`.

Reproduced with a standalone probe replaying exactly `run.rs::seat()`'s sequence on a six-player
table:

```
                       HEAD                              66fd234 (base)
promissory_notes:      4 keys                            24 keys
                       an:generic -> f                   an:a -> a, cf:a -> a, ...
                       cf:generic -> f                   (4 per seat, 6 seats)
                       ps:generic -> f
                       ta:generic -> f
available_notes(a..e): []                                ["an:a","cf:a","ps:a","ta:a"] each
available_notes(f):    ["cf:generic","ps:generic",
                        "ta:generic"]
holder_of("cf", a):    None                              (resolvable)
```

Downstream consequences in every `ti4-sim` game:

- Five of six seats can never offer a note; the sixth offers three phantom `:generic` notes.
- `holder_of`, `denies_movement_into`, `use_ceasefire` and `turn_started` (Military Support) all
  build `note_id(alias, real_faction)` — a key that now never exists. **Ceasefire and Military
  Support are inert.**
- `give_back` and `receive` bail out early because `seat_of(state, "generic")` is `None` once
  real factions are seated, so a `:generic` note can never go home.

**Root cause is architectural, not a missed call site:** `start_game` deals notes it *knows* are
wrong and relies on every caller remembering to re-deal. The fix worth considering is making
`start_game` take the faction assignment (or deferring the deal until seating), rather than
adding a third `deal` call.

### F2 — the smoke test that should have caught F1 was widened instead of investigated (high, process)

`ti4-sim/src/run.rs:487` went from `0..8` to `0..32` seeds with the comment "each seat's random
stream shifted versus the eight-seed sample that first calibrated this guard". That is a
plausible explanation, and the Leadership-eligibility change (F6) genuinely does shift the RNG
stream. But the guard's own docstring says its purpose is that "a harness that measures nothing
can look perfectly healthy" — and 4×-ing the sample to restore a green light is precisely the
move that docstring warns about.

Separately, the guard's event list contains **no promissory event at all**, which is why F1 is
invisible to it. Adding one (e.g. a `TRANSACTION_RESOLVED` / note-transfer event) would close the
gap that F1 walked through.

### F3 — promotion path is recovered by string-prefixing a human-readable message (medium)

`crates/ti4-training/examples/stage2_training.rs`:

```rust
promotion_paths.insert(
    faction.clone(),
    if detail.starts_with("VP") { "vp".to_owned() } else { "clearance".to_owned() },
);
```

`detail` is the operator-facing explanation string built by `own_verdict`. Reword its first
token — e.g. to `"Victory-point merit: …"` — and **every promotion in the checkpoint is silently
relabelled `clearance`**, retroactively corrupting the run record that the two-path experiment
exists to produce. `own_verdict` should return a typed verdict (`enum MeritPath { Vp, Clearance }`)
alongside the text.

Related, same file: `own_verdict` indexes `candidate[faction]` / `champion[faction]` with `[]`.
If a partial rollout failure ever drops a faction from a panel's `metrics`, this panics mid-run
rather than reporting.

### F4 — faction-name identity is not unique, and three call sites resolve it by first match (medium)

The migration replaced seat ids with faction names in ids that must round-trip back to a seat.
Three sites now resolve name → seat by "first match in seating order", each with a comment saying
a duplicate-faction table is outside what the oracle can express:

- `transactions::opens_with` (`component|trade|{faction}`)
- `strategy_cards::politics_primary` (speaker choice)
- `strategy_cards::trade_primary` (free replenishment)
- plus `action_cards::signal_jamming`, which builds `rivals` keyed by faction name and picks the
  first match — a duplicate-faction table would jam the wrong seat's token.

The premise is fine *for the oracle*, but the Rust engine's own default table is six seats all
called `"generic"`, and `fixtures::game()` produces exactly that. Several tests had to be edited
to seat real factions to keep working (`wiring.rs:248`, `promissory.rs:434`, `transactions.rs:1325`).
So the engine is now correct only on tables it does not construct by default. Worth either
(a) making `"generic"` seats impossible, or (b) keeping the seat id in the id and the faction
name in the label/payload.

`reactions::slot` also folds the seat id out of the ability id
(`reaction:{faction}:{event}:{relation}`). This one is **not** a bug — `eligible()` filters on
`ability.owner`, and the slot's `Frequency::Unlimited` means `scope_key` returns `None`, so the
shared id never shares a use budget. I checked this specifically; noting it so the next reader
does not have to.

### F6 — `secondary_choice` dispatches on a content-derived display string (medium)

`crates/ti4-engine/src/strategy.rs:64` and `strategy_cards.rs:889` both branch on
`card_name(content, ...) == "Leadership"`. The behaviour change is real and correct (52.3 gates on
influence, not a strategy token, so unaffordable followers make *zero* decisions), but the
dispatch key is the human-readable card name from the content store. A localisation, a rename, or
a second source set that spells it differently silently reverts Leadership to the generic
token-gated path. The `StrategyCardId` (`te4leadership` or similar) is already in hand and is the
stable key.

Same pattern, different flavour: `strategy_cards::trade_primary` now hard-codes
`seat.faction.as_str() != "generic"` inside engine logic to exclude scaffolding seats from
replenishment. That is test scaffolding leaking into production rules.

### F7 — `buy_tokens_with_influence` and `buy_tokens_first_yes_assumed` are near-duplicates (low)

`strategy_cards.rs`: the second function is the first with one `pay_influence_and_gain_one` call
hoisted above the loop. The loop body — ask, `if answer.id != "yes" { return }`, pay, `if !paid {
return }` — is copy-pasted. A single `fn buy_tokens(..., first_yes_assumed: bool)` or a
`loop { … }` with the first iteration's ask skipped would keep the two paths from drifting.

### F8 — `finish_game` measures the opening baseline twice per rollout (low, perf)

`rollout.rs`: `play_assigned_on_map_shared` calls `opening_baselines(...)` to seed each bot's
`from_setup`, then hands the state to `finish_game`, which calls `opening_baselines(...)` again on
the same unmodified state. Identical result, doubled cost — and `Baseline::taken` walks the whole
observed board per player. On a six-seat panel that is 12 full board scans per game where 6 would
do. Passing the already-computed map into `finish_game` (with `play_with_deciders` computing its
own) removes it.

### F9 — `--no-boundaries` still pays for three bootstrap panels (low)

`stage2_training.rs`: the `--no-boundaries` flag is checked inside the update loop, but the three
startup panels (`initial_candidate`, `accepted_panel`, `accepted_confirmation_panel`) are
evaluated unconditionally before it. In "pure learning, champion frozen" mode none of the three is
ever read again. For a 32-seed × 6-rotation panel that is ~576 discarded games at launch.

### F10 — `panel_probe` indexes past the end of `args` on a trailing flag (low)

`examples/panel_probe.rs:12–22`: `"--checkpoint" => { i += 1; checkpoint = Some(args[i].clone()) }`
panics with an index-out-of-bounds if the flag is the last argument. Diagnostic tooling, so
low-impact, but the failure is a backtrace rather than the `usage:` line it already knows how to
print.

### F11 — `FactionPlan` is a public struct with literal construction sites (low, design)

Four new public fields (`train_seed_stride`, `high_vp_bonus`, `clearance_weight`, `pipeline`,
`rollout_depth`) forced edits in `examples/stage1_other_factions.rs` and both
`FactionPlan::*_reference()` constructors. Each future experiment flag will do the same.
`#[non_exhaustive]` plus a `..Default::default()` idiom, or a builder, would make this additive.

Related trap: `train_seed_stride` defaults to `16`, matching the *default* `train_seeds`. Anyone
who sets `plan.train_seeds` directly without also setting the stride gets overlapping training
seed blocks across updates. `stage2_training.rs` gets this right
(`plan.train_seed_stride = train_seed_stride.unwrap_or(plan.train_seeds)` after assigning
`train_seeds`); `stage1_other_factions.rs` hard-codes both to 16 and is fine today, but the
coupling is implicit.

### F12 — dead/odd parameters kept for symmetry (low)

- `promissory::trade_agreement_worth` now opens with `let _ = state;` — the parameter exists only
  "for call-site symmetry with the oracle's game-taking form". Defensible, but it means the
  function's signature lies about what it reads.
- `strategy::pending_choice` computes `costs_token` and then passes it to `secondary_choice`,
  which discards it on the Leadership path.
- `reward::returns` guards both new terms with `> 0.0`, silently ignoring a negative
  `high_vp_bonus` / `clearance_weight` rather than applying or rejecting it.
- `transactions::faction_name` and `promissory::faction_name` are the same function in two
  modules; `transactions::offer_from` calls the promissory one while `transactions::priced` calls
  the local one.

### F13 — `run_batch_group`'s doc comment contradicts its body (trivial)

`stage1.rs`: *"Play several updates' rotated batches in one shared wave (Python map pool only)."*
The `match map_pool { None => …, Some(pool) => … }` handles both. Same for the `#[must_use]`-less
`play_with_deciders` doc that says trajectories are "empty unless the deciders themselves record
them" — accurate, but the neighbouring `handles: None` argument makes it look like a bug at the
call site.

## Things I checked and found correct

Recording these so the next reviewer does not re-derive them:

- **`py_round_half_even`** — exact for every value the `NOTE_WORTH` table can produce (whole
  numbers and binary-exact `.5`s). `floor % 2.0 == 0` correctly selects the even neighbour.
- **`pn{note}:{price}` parsing** — `rsplit_once(':')` is right, because the note id itself is
  `alias:faction`. `ac{card}:{price}` correctly uses `split_once`, since card aliases carry no
  colon.
- **`production::settle` cannot spin** — every payment face has `worth >= 1` (`payment_faces`
  drops zero-value faces, trade goods are worth 1 or 2), so `owed` strictly decreases.
- **`apply_payment_option`'s id reparse** — the `(Some(source), Some(pos)) if source != kind`
  guard correctly avoids splitting planet ids that themselves contain `|`.
- **Reaction slot id collisions** — harmless, per F4's note on `Frequency::Unlimited`.
- **`play_rotated_map_group_statistics` group demux** — `par_iter().collect()` preserves job
  order, so the `per_group[group].push(...)` reassembly is deterministic; the round-trip is
  covered by `a_group_wave_matches_sequential_groups_with_frozen_profiles`.
- **Evaluation-only rollouts (F15)** — `an_evaluation_rollout_matches_the_recording_rollout_on_finals`
  asserts final progress, `cleared` and `shortfall` are bit-identical, which is exactly the
  property `evaluate()` depends on.
