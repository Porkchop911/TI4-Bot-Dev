## Generated input contracts

Each property runs 128 deterministic Proptest cases. Generated registries contain at most 24
abilities across two owners, two relations, matching/nonmatching event types, enabled/disabled
conditions, all four frequency modes, and both repetition settings.

- Every generated effect consumes a shared eligibility resource. This models an unlimited
  repeatable reaction slot correctly: it remains repeatable only while a playable backing resource
  exists. The Python oracle intentionally leaves that condition to the rule, so an inert,
  unconditional unlimited-repeatable callback is outside the terminating-input contract in both
  implementations.
- Frequency cases emit four events across two ordinary events, a turn advance, and a round
  advance. They establish exact counts of 4 for per-trigger/unlimited, 3 for per-turn, and 2 for
  per-round abilities.
- Duplicate-ID cases keep `repeatable_in_window` false and assert at most one resolution for each
  identifier in one timing window. Optional-pass cases use a deterministic declining table and
  assert at most one pass per seated player.

## Tests added

1. Generated legal self-consuming registries terminate and resolve no more than their initially
   matching enabled slots.
2. Generated frequency assignments use each scope no more or less than allowed across lifecycle
   transitions.
3. Generated disabled or event-mismatched abilities never execute.
4. Generated duplicate non-repeatable IDs resolve at most once per timing window.
5. A generated registry produces the same complete public trace when constructed and run twice.
6. Generated optional registries with an always-declining table terminate without an ability
   effect and with no more than two passes.

## Implementation and compatibility evidence

- The suite uses the already-pinned `proptest` development dependency; no dependency or lockfile
  change was required.
- The termination property does not impose an arbitrary Rust-only resolution/pass cap. Such a cap
  would diverge from the oracle's repeatable reaction slots and conceal the rule condition that
  makes them stop. Instead, every generated repeatable/unlimited case consumes its condition,
  exactly as a playable reaction resource must do.
- The generated conditions, event types, duplicate IDs, and lifecycle transitions test the same
  resolver filtering boundaries as the focused M03-009 through M03-012 conformance tests.
