## Result

1. **The gap.** Under the completed prompt-free contract (`OBS-003i`), a casualty or sustain
   option's identity was `destroy|0`/`sustain|1` — a bare index with **no** structured content once
   the display label (which alone named the unit type) is dropped. Two such options were
   indistinguishable to the policy.
2. **Engine.** Both option-building sites for casualty (`choose_casualty`, and
   `CombatWindow::pending_choice`'s `Assigning` stage, which duplicates rather than shares the
   logic) now attach `.with("unit", type_id).with("damaged", sustained_damage)`. Both sites for
   sustain (`offer_sustain`, and the `Sustaining` stage) attach `.with("unit", type_id)` only —
   every sustain candidate is filtered to `!sustained_damage`, so a `damaged` key would always read
   `false` and carry no information.
3. **No new feature-layer wiring needed.** `canonical_feature_kind` already maps both the raw
   `casualty` and raw `sustain` kinds to the canonical kind `"casualty"`. `structured_features`'s
   existing generic tail (`if let Some(unit) = payload_string(option, "unit") { add_unit_features
   (seen, unit, "casualty-unit", features) }`) therefore already fires for both kinds the moment the
   payload exists — this package supplied only the missing payload, not new code in `features.rs`.
4. **Approval.** `casualty-unit` joins `projection::APPROVED_UNIT_FAMILIES` (5 → 6 entries),
   resolving through the existing `APPROVED_UNIT_FAMILIES.contains(&family)` check to the shared
   `UNIT_SUFFIX_FAMILY` (`"*-unit"`) reserved OOV column every other approved unit family already
   shares — no new column, no registry version bump. This is the architecture-review decision the
   family's own doc comment calls out; it is made under the same standing "continue, independent
   review deferred" instruction the rest of this workstream has used, and is part of what that
   review must check.

## Focused evidence

- `combat.rs::obs008b1_casualty_and_sustain_options_carry_their_unit_identity`: a fresh and a
  damaged dreadnought are distinguishable casualty options, each naming `unit: "dreadnought"` and
  the correct `damaged` flag, through both the standalone `choose_casualty` and the windowed
  `Assigning` stage; a sustain option names `unit: "dreadnought"` with no `damaged` key, through
  both the standalone `offer_sustain` and the windowed `Sustaining` stage.
- `features.rs::obs008b1_casualty_options_expose_the_named_units_own_stats`: a `casualty` option
  carrying `unit: "dreadnought"` emits `casualty-unit:is-ship` and `casualty-unit:sustain` (and no
  `casualty-unit:is-fighter`); a `sustain` option carrying `unit: "carrier"` emits the *same*
  family (`casualty-unit:is-ship`, `casualty-unit:capacity` — the canonical-kind unification); both
  survive `mlp_option_features` and `projection::admits`.
