## Invariants and compatibility contract

- A scope key is `(ability ID, trigger event ID)`, `(ability ID, turn number)`, or `(ability ID,
  round number)` exactly for the three bounded frequencies; unlimited abilities have no key.
- The key is inserted before the ability callback, preserving the oracle's behavior if that callback
  emits another event or returns an error.
- `begin_turn(player)` increments the turn counter and sets the active player. `begin_round()`
  increments both round and turn counters atomically. Counter overflow returns a typed error.
- The oracle retains its used-key set and advances counters rather than clearing old entries. Rust
  does the same; old keys cannot match future scopes and trigger IDs are trace-unique. This corrects
  the stale placeholder evidence's inaccurate cleanup claim.
- Frequency filtering occurs in addition to the per-window `resolved_here` rule. It does not
  alter relation, owner, condition, or generated-choice legality filtering.

## Tests added

1. Once-per-trigger resolves independently for distinct event IDs.
2. Once-per-turn blocks later events in the same turn and reopens after `begin_turn`.
3. Once-per-round remains blocked across a turn and reopens after `begin_round`.
4. Unlimited resolves across events, turns, and rounds.

## Implementation and compatibility evidence

- `Resolver` stores an ordered set of `(ability ID, FrequencyScope)` values. Trigger keys use the
  event's trace-local numeric ID, while turn/round keys use the matching monotonic lifecycle
  counters; unlimited returns no key.
- Eligibility checks frequency after exact bucket/owner/window filtering and before condition
  evaluation. A selected ability records its key before invoking its fallible effect, mirroring the
  oracle's pre-effect mark.
- Lifecycle counters begin at one and use checked increments. `begin_round` calculates both new
  values before mutation so an exhausted turn counter cannot leave an incremented round behind.
