## Step one — the version check the package gated itself on

The spec required this to be established *before* anything reached `Cargo.toml`, because the whole
cheap path rested on it. Result: **the newest `tch` does not match the installed torch, but an
older one does.**

| `tch` | requires libtorch | vs installed 2.9.1 |
|---|---|---|
| 0.26.0 (newest) | **2.13.0** | mismatch — would need the ~2 GB download |
| 0.24.0 | 2.11.0 | mismatch |
| 0.23.0 | 2.10.0 | mismatch |
| **0.22.0** | **2.9.0** | **patch-level; accepted by the build** |
| 0.20.0 | 2.7.0 | mismatch |

Read from each release's own README in the crates.io source, not from memory. `tch` publishes no
0.21 or 0.25.

`tch` is MIT/Apache-2.0. Its `download-libtorch` feature is **opt-in and was never enabled**, so no
libtorch was fetched at any point.

## The pin is bytes, not a version string

Per the spec's provenance objection — linking at a path inside a user-local Python installation is
not a pin, because `pip install --upgrade torch` would silently change the native library this
project links against — libtorch was **copied once** rather than referenced in place:

```
out/libtorch-2.9.1-cpu/{lib,include,share}     9,311 files, 367.6 MB   (gitignored)
plans/artifacts/libtorch-2.9.1-cpu.manifest.json                        (committed, 4 KB)
  tree_sha256  b9f97c5783db935ce3858f17ee8808235066ae2102004f17215545c55662c364
  lib_files    27 rows, per-file SHA-256
```

The manifest is deliberately two-level. One rolling `tree_sha256` over every file's path, size and
content in a fixed walk order detects any drift anywhere without carrying 9,311 rows in a diff — a
per-file listing came to 1.6 MB and would have made every future review of this file unreadable.
Per-file rows are kept for `lib/` alone, because those 27 binaries are what actually gets linked and
loaded, so a change there is the one that changes what the process runs.

## CPU-only load — proven, not asserted

Built `tch = "=0.22.0"` against the pinned copy in a throwaway crate outside the workspace, then
ran it:

```
cuda available: false
device count: 0
sum: 6
```

Both halves matter: the library loads and does arithmetic, and it reports **no CUDA**, which is
§7.1's requirement that CUDA is never an inference backend on this branch.

**The Windows friction §8 predicted is real and is now characterised.** The first run failed with
`STATUS_DLL_NOT_FOUND` (0xc0000135) because a Git Bash `PATH` is not what the Windows loader reads;
it needs a Windows-style `PATH` with the pinned `lib` directory on it. That is an environment
requirement the package must record and the adapter's tests must set, not a defect.

The probe crate was deleted. Nothing was added to the workspace: `Cargo.toml` and `Cargo.lock` are
untouched, and the only new tracked file is the manifest.

## The decision this surfaces

Two coherent pins, and the choice is not mine:

| | **A — `tch` 0.22.0 + libtorch 2.9.1** | **B — `tch` 0.26.0 + libtorch 2.13.0** |
|---|---|---|
| download | **none** | ~2 GB libtorch distribution |
| proven here | **yes, builds and runs** | not attempted |
| currency | four releases behind | current |
| version gap | tch targets 2.9.0, runs on 2.9.1 | exact |
| risk | an older API surface; upstream fixes since 0.22 unavailable; the patch-level gap is accepted by the build script but is not an upstream-tested pairing | a second 368 MB copy on disk alongside the Python install, and a new download to review for licence/advisories |

A is what the authorization contemplated and it works. B is what the plan would have chosen if the
machine had been empty. I have not taken this: pinning a dependency four releases back is a
decision with a tail, and §7.2's determinism requirements (`set_num_threads`, deterministic-algorithm
mode) must be checked against whichever API is pinned before either is final.
