### Design decisions made during implementation (recorded before review)

1. **W1 plays one *complete* game per sample, not a fixed step budget.** The original spec said
   "run to the 20,000-step limit" with a gate requiring `RunError::StepLimit`. Measured against
   all 40 manifest seeds (`w1_ending_diagnostic`, env-gated): **every game ends by objective-deck
   exhaustion at round 9** regardless of play style (all 40: `finished=true round=9`). A fixed step
   budget would cut games off mid-shape, so the workload was redefined as "play to natural
   termination" with per-decision normalisation (`table.log.records.len()`, the same metric as
   `GameResult.decisions`); 20,000 steps / round cap 50 remain safety bounds that must not bind.
   The spec's W1 section was updated in-package before any measurement was taken.
2. **Scope constant corrected.** The spec originally wrote `SourceSet::default()` (= FULL). That is
   wrong: `SourceSet` is an `EnumSet`, whose `Default` impl is the *empty* set — setup fails with
   "no strategy card set". Runtime paths use `content_types::DEFAULT` (= FULL) per its doc contract;
   code and spec now say so.
3. **Path resolution.** `cargo test` runs with CWD = package dir while examples run at the workspace
   root (both verified empirically). The campaign takes an explicit repo root resolved from
   `CARGO_MANIFEST_DIR` (`repo_root()`), so it works under either invocation.

### Variance verdicts (honest reporting)

All three workloads are **unstable** under the predeclared M00-012e thresholds on this host — a
valid baseline outcome per spec. Structure of the noise, from the raw samples:

- W1's spread is genuine between-board variance (different boards produce different amounts of
  combat/exploration work); stdev % ≈ 9.8–10.2 in both builds.
- W2/W3 show a **monotonic upward drift** across the 30 samples (release W2: 53,000 → ~60,000 ns
  with one 110,100 outlier; W3: 7,200 → ~9,900 with one 14,000), i.e. an absolute jitter floor of
  roughly ±10–20 µs on this shared dev host (frequency scaling / background load). That floor is
  small relative to a 46 ms game but large relative to 8–60 µs operations — which is why the debug
  build's longer measurement windows show *lower* relative variance.

**Consequence for rows 021–023:** any optimization claim on feature extraction or model scoring
must use paired, interleaved A/B measurements (same session, same machine), not standalone re-runs
compared against these bounds — consistent with the M00 protocol's no-speedup-without-protocol
rule and the M08-021 bootstrap discipline. These numbers are context anchors only; they are not a
gate and were never intended to be one.

Context (not a gate): pre-rules aggregate ~450 µs/decision (MLP plan §10, release-mode training
work). W1's engine-only 44.5 µs/decision plus W2+W3 ≈ 6.3 µs/option × 11 options ≈ 70 µs per
production decision leaves the remainder of that aggregate in training-loop overhead and
multi-head work outside this profile's scope.
