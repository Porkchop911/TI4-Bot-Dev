## Invariants and compatibility contract

- The registry partitions abilities by exact event type and `WHEN`/`AFTER` relation.
- Each partition retains insertion order; resolution must never depend on map traversal.
- Ability fields preserve the oracle's ten data/callback fields. Rust callbacks receive the
  concrete `Resolver`, so M03-010 can add emission without an untyped game-object boundary.
- Frequency is metadata only in this package. M03-012 owns scope keys and lifecycle mutation.
- Absolute "cannot" predicates are persistent and `is_forbidden` returns the first matching
  registration, as in the oracle.
- Duplicate ability identifiers remain registered: Python registration accepts them, so M03-009
  does not invent a rejection rule. The resolver will own per-window identifier semantics.

## Implementation and compatibility evidence

- `Ability` contains the oracle's ID, owner, event type, relation, effect, condition, frequency,
  optional, repeatability, and option-payload fields. It defaults to once per trigger, mandatory,
  non-repeatable, and no optional callbacks, matching the frozen Python dataclass.
- `AbilityRegistry` indexes each registration under its exact event type and relation in a
  `BTreeMap`, but resolves through stored insertion indexes. Therefore neither registration nor
  candidate lookup depends on map iteration order.
- `forbid(label, predicate)` retains predicates forever and `is_forbidden` returns the first
  matching label. No removal or enabling override is exposed.
- Callback boundaries use `Arc` and the concrete `Resolver`: M03-010 can add mutation and nested
  emission without changing every registered rule callback. The resolver now owns the registry
  and exposes the oracle-shaped `register`, `forbid`, and `is_forbidden` methods.
