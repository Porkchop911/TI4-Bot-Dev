## Campaign 2 — effect markers cannot leak across sequence identities or survive decline/error/early exit

Every sequence-scoped marker is identity-checked against a **monotonic** counter at its read site;
a stale value can therefore never match again:

| Marker | Set site (atomic with payment) | Read site (identity check) |
|---|---|---|
| `combat_bonus_round` (Morale Boost) | action_cards.rs:266, on card play | combat.rs:125 — `== Some(state.combat_round_seq)` |
| `extra_die_round` (leader) | leaders.rs:485, on leader resolution | combat.rs:179 — `== Some(state.combat_round_seq)` |
| `munitions_round` (Letnev) | faction_abilities.rs:680, after a successful non-declined ask; payment and marker set in the same block | combat.rs:147 — `== Some(state.combat_round_seq)` |
| `move_bonus_activation` (Flank Speed) | action_cards.rs:277, on play | action_cards.rs:1462 — `== Some(activation)` against `activation_seq` |

- `combat_round_seq` is initialized 0 (state.rs:932) and only ever `saturating_add(1)`
  (combat.rs:1021 space rounds, invasion.rs:487 ground rounds). It never resets.
- **Decline/error paths set nothing**: the munitions hook returns before payment on decline or ask
  error (faction_abilities.rs:669-675); failed transitions are atomic per project law, so no
  partial marker state survives an error.
- Early combat exit (barrage wipe) leaves any round marker inert — the counter only moves forward.

**F-M07-020-1 (informational).** `Seat::ground_roll_suppressed_round` and
`Seat::sustained_damage_round` are defined in state.rs:363/366 and compared in `PartialEq`, but
have **no read or write site anywhere in the engine** — inert reserved fields. No leak risk
(nothing reads them); recorded for registry completeness so a future package that implements the
abilities they name must add both the set site and an identity-checked read site, with tests.

## Campaign 3 — observer views and authored-bot inputs: secret identity/eligibility leakage

- **The boundary is typed.** `Decider::choose_seeing(&Choice, &Observed)` (choice.rs:702) is the
  only seam; raw state never crosses it. `Observed` holds its state privately and every accessor
  answers a public fact ("Only public facts are reachable through this type", choice.rs:403);
  hand contents are reachable only through the deliberately-named `redacted_for`.
- **Redaction semantics** (both implementations agree): other players' `action_cards` and
  `secret_objectives` become `HIDDEN = "?"` markers with counts preserved; own state untouched.
  Engine: `choice.rs::redacted_for` (632). Policy: `ti4-policy/src/view.rs::view_for`. Both are
  pinned by tests, including a check that an unredacted state is reported as leaking.
- **Correction of this campaign's original claim (review R2):** the first draft of this file said
  the leak check was "guards-the-guard" — that *a newly added private field fails a test instead
  of leaking quietly*. That assurance is false. `leaks()` (`ti4-policy/src/view.rs:85`) iterates
  exactly the two fields `redact_player` redacts, by hand; it is a mirror, not an enumeration over
  `Player`. A third private field would be missed by both. **M06 is the proof case:**
  `Player.event_feats` was added during M06, is covered by neither implementation, and `leaks()`
  stayed silent — no actual leak today only because `event_feats` holds table-public occurrence
  ids (M07-019 review M4). The mechanism this gate relied on demonstrably did not fire when tested
  by real events. **Deferral, in writing:** making the check field-complete is a separate, larger
  question — no package scoped at M07 closure; recorded as `ML-1` in `plans/KNOWN_DIFFERENCES.md`
  with the condition that any future package adding a private field to `Player` extends both
  redaction implementations and the leak check in the same commit, red-first.
- **Bot inputs**: rollouts seat `Box<dyn Decider>` per player (rollout.rs:650-671); baselines and
  progress are measured through `Observed` only. The authored bot's one identity inspection —
  `score_objective` reading an objective's printed points — is sound by construction: it inspects
  only objectives the engine already offered as legal choices, which are private to their owner
  (documented at bot.rs:640).
- **F-M07-020-2 (informational, reaffirmed).** `GameState::promissory_notes` is a table-wide map
  and cannot be redacted per player; views therefore expose who holds which note. This is the
  documented, named gap `UNREDACTED = ["promissory_notes"]` in ti4-policy/src/view.rs with a
  naming test (`the_gaps_this_view_still_has_are_named`). No change since M08-001; carried into
  the milestone known-differences ledger.

## Occurrence-scoped scoring contract — reaffirmed against rule 61.7 as adjudicated in M06-021a

The exit review rechecked the one-per-combat cap end to end:

- `EventScoreLimit` (objectives.rs:1467) documents 61.7: "at most one objective during or after
  each combat; any number during an action turn or agenda phase."
- The cap is enforced **by occurrence membership, not window membership** — M06-021a F1's option
  (b): `state.record_occurrence_score(&player, occurrence)` on every OnePerPlayer score
  (objectives.rs:1679-1683), and an already-scored player is offered no secrets in any later
  window for the same occurrence (objectives.rs:1600-1608). Two windows for one combat occurrence
  cannot double-grant.
- The invasion `combat` flag implements M06-021a F2's adjudication — ground combats are per
  planet, each carrying its own cap (`OnePerPlayer`); control-loss facts (home loss) and
  bombardment are not combats and open `AnyPerPlayer` windows. A home loss in an invasion that
  also contained a ground combat therefore yields two distinct occurrences with independent
  limits — exactly the accepted interpretation, not a new question.

## Adjudication of F-M07-019-1 (review R1)

M07-019 escalated this finding to a frontier-model adjudication before any fix package could be
scoped, and this gate is that adjudication. **Decision: option 2 — accept as a recorded known
difference with the scoped fix deferred to M08.** Reasoning:

1. **The rules deviation is real and not rejectable on rules grounds.** LRR 49 was verified in
   M07-019 (web consultation, recorded there): a planet without enemy ground forces falls without
   resistance; PDS/Space Dock are not ground forces. Option 3 is unavailable.
2. **Fixing inside this gate would break comparability mid-milestone.** The change alters invasion
   legality/timing semantics — the same class of behavior change that M06-025 handled as its own
   numbered package with full review and a re-baseline note (KD-1). Doing it here, at the exit
   gate, after all four frontier packages were accepted against current behavior, would invalidate
   their baselines silently.
3. **Deferring to M08 before 018 keeps everything comparable going forward.** M08's accepted
   baseline was built on this same M05-era behavior; ordering the fix *before* M08-018 means bot
   revalidation and every downstream training baseline run against corrected behavior exactly once,
   with no mid-milestone re-baseline. The blast radius is bounded (adjudicated in the review):
   structures roll no dice, so the invader always wins the spurious fight; final control outcome
   unchanged.
4. **The one concrete consequence — L1Z1X Assimilate's structure conversion being unreachable
   through `InvasionWindow`** — is a faction-ability gap that M08-020 fixes, with the
   Assimilate-after-pause coverage (M07-019 review M1c) as its required deliverable.

Recorded as **KD-2** in `plans/KNOWN_DIFFERENCES.md`; scoped package at
`plans/M08-020_GROUND_COMBAT_STRUCTURE_LEGALITY.md`; milestone row added to
`plans/M08_AUTHORED_BOTS.md` with M08-018's dependency updated accordingly.
