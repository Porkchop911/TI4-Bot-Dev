## What was done

Three changes, all in `crates/ti4-engine/src/combat.rs`:

1. **New test** `a_stepped_combat_matches_the_driven_one_across_a_barrage_pause` — the pausing
   fixture from `a_driven_combat_continues_after_its_barrage_scoring_pause` (destroyer×1 vs
   fighter×1 + cruiser×1, faces `[10, 10, 10, 1]`, seed 1): the round-1 AFB barrage destroys the
   defender's only fighter, fires `BarrageTookTheLastFighters` for the attacker, and pauses for
   scoring. The same fight is stepped by hand and driven through `resolve()`; outcomes must match
   and final states must be identical — **including** an explicit assertion that the barrage feat
   is recorded on *both* sides (identity alone would also pass if neither side had fired it).

2. **Shared completion helper** `complete_window` (production code, next to `resolve()`): returns
   the window's outcome and records event feats at completion — exactly the bookkeeping both real
   drivers perform. `resolve()`'s tail now calls it (behavior-preserving refactor: same sequence,
   same discarded result), and the stepped harness calls it too. A third copy of this bookkeeping is
   structurally impossible from here on (review N2's factorization). The Game driver keeps its own
   inline bookkeeping — there a noted occurrence pauses for scoring *before* the fight is over, so
   it cannot share the helper; documented in the helper's doc comment.

3. **Stepped harness** `stepped_fight` (test module): manual settle / pending_choice / resolve loop
   with pause consumption mirroring `resolve()`'s pump — when no choice is pending and the fight is
   not over, it calls `take_scoring_occurrence()` then `settle_open()`, exactly as `resolve()` does
   after each `drive()`. Both equivalence tests now use this one harness shape (the old inline
   stepped branches were replaced by calls to it), so they cannot drift from each other or from the
   shared completion helper.

## Design decisions recorded

- **Two-table structure kept in `stepped_fight`** (the context keeps its own table; asking goes
  through a separate parameter): one long-lived `Resolving` borrows that table for the whole loop,
  so borrow-checking requires a distinct ask table. Neither table is asserted on in these tests, and
  the fixture's generic factions produce no faction offers — behavior-neutral. `resolve()` uses one
  table because `Window::drive` asks through `ctx.table` internally; documented at the site.
- **`settle_open` is `settle`** (combat.rs:1110) and `take_scoring_occurrence` is a harmless `.take()`
  when nothing is pending (combat.rs:933), so the no-choice branch is safe to run on every
  non-pausing iteration — the loop degenerates to the old shape for fights that never pause.
- **The Game driver was not re-pointed** at `Game` itself (deferred to M07-020's scope decision per
  the M07-021 evidence), and its deliberate snapshot difference (`before_combat_with_notes` vs plain
  `before_combat`) is untouched.

## Behavior change note

None. The production diff is a behavior-preserving refactor of `resolve()`'s tail into
`complete_window` (same sequence, same discarded result — verified by the full suite passing with
no count change beyond +1 test). No serialized format, choice ID, canonical projection for replay
hashes, registry, or scoring behavior changed. The only new runtime surface is a private helper and
a test-module harness.

## Coverage limit recorded per review P2 — a pause that decides nothing

The reviewer instrumented both equivalence tests and found the two branches of `stepped_fight`
each covered but never composed:

| test | pause branch | choices asked |
|---|---|---|
| `a_stepped_combat_matches_the_driven_one` | never | 1 — "assign a hit" |
| `…_across_a_barrage_pause` | once | **0** |

The pausing fixture pauses, resumes, and ends without any decision pending: nothing verifies that
the stepped driver resumes *into a choice* at the retained frame. That composition is exactly the
failure mode M07-019's charter names first ("a faction reaction in flight when the window opened
must resume at the exact retained frame; the failure mode is a skipped or doubled effect, not a
crash") — pinned through `Game` by M07-019, but not for the synchronous API and its replica, which
is what this package is about. The equivalence invariant is therefore verified across a pause that
decides nothing.

**Corrected claim:** equivalence holds on `event_feats` across a scoring pause **with no choice
after it**. This is the same shape of overstatement N1 corrected one step earlier; recorded here so
the chain's claims match its tests. It does not undo what this package achieved — the pause path is
now exercised and the harness can traverse it — but the composition case remains open.

**Scoped successor: M07-023** (prep spec `plans/M07-023_POST_PAUSE_CHOICE_COMPOSITION.md`,
milestone-plan row added) — extend the pausing fixture so the fight continues past the barrage into
a casualty assignment (more cruisers on the defender, dice that leave hits to absorb), or add a
third fixture that does. Per P2's recommendation it is scoped **before** M07-020's exit review and
is now a dependency of it.

## P3 recorded — helper content is no longer independently checked

Sharing `complete_window` removed the last independent check on its *content*: both equivalence
tests now call the same four lines, so a bug inside the helper would make them agree on the wrong
answer. This is the correct trade and exactly what N2 asked for (drift between copies was the bug
class that actually bit, twice). Recorded per P3 so a green equivalence test is not later cited as
validating the bookkeeping's content: what validates that content is
`a_driven_combat_continues_after_its_barrage_scoring_pause`, which asserts the feat against
`resolve()` directly.
