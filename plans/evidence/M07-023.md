## What was done

One new test, `a_stepped_combat_matches_the_driven_one_across_a_pause_and_assignment`, added to the
`combat.rs` test module (+67/−0; no production code touched). It closes the composition P2 named:
the fight pauses for scoring, resumes, and then reaches a choice at the retained frame — the stepped
driver must answer it.

**Fixture design** (per P2's suggestion): attacker destroyer×1 vs defender fighter×1 + cruiser×2 in
the arena system, faces `[10, 10, 10, 1, 1, 10, 1]`, seed 1:

| Phase | Dice consumed | Effect |
|---|---|---|
| Round-1 AFB (barrage) | `[10, 10]` | both hit the fighter (afbHitsOn 9); fighter destroyed; `BarrageTookTheLastFighters` fires for the attacker → **scoring pause** (`RollingAfterBarrage` + pending occurrence) |
| Round-1 combat roll (resume) | `[10]` then `[1, 1]` | attacker's destroyer hits once; both cruisers miss. No sustainers (generic factions), so `Sustaining` cascades to `Assigning`: one unabsorbed hit across two ships → **choice "assign a hit"** — the first choice of the fight, and it comes after the pause |
| Round 2 | `[10]` then `[1]` | attacker hits again; defender's last cruiser auto-assigned (a single possible casualty is not a decision); `over()` → conclude, attacker wins |

**Assertions:**

1. Outcomes equal on both sides.
2. `BarrageTookTheLastFighters` recorded on **both** final states (identity alone would pass if
   neither side had fired it — same guard as M07-022).
3. **Both decision logs contain an "assign a hit" record for the defender.** This is deliverable
   2(a)'s non-vacuity guard: `Table::ask` records every choice in `table.log`, so if a future
   fixture change stops producing the post-pause assignment, this assertion fails informatively.
4. `stepped_log == driven_log` — full decision-sequence equivalence (both sides were asked the same
   choices, in the same order, and answered identically under the default decider).
5. Final states identical (`identical()`, which reaches `event_feats` via M07-021's equality fix).

**Why "any recorded ask is necessarily after the pause" holds for this fixture:** the window opens
at `Announcing`, but `retreats()` is empty in the arena system, so it cascades without a choice;
the `Rolling`/`RollingAfterBarrage` stages return `None` from `pending_choice`. The only stage that
can offer a choice before the barrage would be `Announcing` with available retreats — empirically
absent here (M07-022's instrumentation of the same arena recorded zero choices in its pausing
fight). Recorded at the test site as well.

## Red-first / non-vacuity probe (deliverable 2(b))

Per the spec: run the fixture against a harness without pause consumption (the pre-M07-022 shape)
and record the failure, proving the fixture really pauses. Probe applied to `stepped_fight`'s
no-choice branch (`break` instead of `take_scoring_occurrence()` + `settle_open()`), then reverted:

```text
a_stepped_combat_matches_the_driven_one_across_a_pause_and_assignment ... FAILED   (panic at combat.rs:2739, .expect("the fight resolved"))
a_stepped_combat_matches_the_driven_one_across_a_barrage_pause          ... FAILED   (same panic)
a_stepped_combat_matches_the_driven_one                                 ... ok
```

Both pausing fixtures fail against the old shape — including this one, which additionally proves
the fixture pauses *and* that consumption is what lets it reach the assignment choice. The
non-pausing test stays green under the probe (the loop degenerates to the old shape for fights
that never pause). Probe reverted; all three tests re-run green afterwards.

## Design decisions recorded

- **Third sibling test rather than extending M07-022's fixture.** Extending would have destroyed
  the suite's only dedicated coverage of "pause with no choice after" (the exact case P2 says is
  currently covered). Adding a sibling preserves both compositions: pause→end and pause→choice.
- **Log-based assertion instead of a counting wrapper.** `Table` already records every decision in
  its public `DecisionLog` (`ask` → `settle` → `record`), which derives `PartialEq` — so the guard
  needs no new type, no harness signature change, and additionally yields the full-sequence
  equivalence check (assertion 4) for free.
- **No production code changed.** The composition was already correct in the engine (M07-019 pins
  it through `Game`); this package pins it at the synchronous-API level, which is what the
  M07-021/022 chain protects. Deliverable 3's escalation path was not needed.

## Review resolutions applied (Tier B, Claude Opus 5)

**Accept**, with Q1 and Q2 applied inside this package per the reviewer's disposition ("this chain
should end here and M07-020 should proceed"). Both are single assertions in a function this
package already owns; neither is new behavior or scope.

- **Q1 (MEDIUM) — ordering now asserted, not argued.** `stepped_fight` returns the outcome plus
  how many choices had been asked when the first scoring pause was consumed (`Option<usize>`;
  consumption stays unconditional so the harness still mirrors `resolve()` exactly). The test
  asserts `stepped_asks_before_pause == Some(0)`: the fixture pauses, and no choice may be asked
  before the barrage pause — so every recorded ask (the assignment included) came after it. A
  future fixture change that lets a choice precede the barrage now fails informatively instead of
  leaving the test green while it stopped testing the composition.
- **Q2 (LOW) — log-comparison integrity guarded.** `stepped_fight` ends with
  `assert!(ctx.table.log.records.is_empty(), …)`: if a future fixture ever routes an internal ask
  through the context's table (e.g. faction combat-round offers such as Letnev Munitions Reserves),
  it fails informatively instead of silently comparing split logs against the ask-table-only log.
  The two-table comment at the site was updated — M07-022's "neither is asserted on" wording was
  stale once the log-equality assertion landed, and the reviewer was right that the structure had
  become load-bearing without anyone noticing.

## What this pins — and what it does not

Pinned: (a) the stepped driver resumes **into a choice** at the retained frame after consuming a
scoring pause; (b) that ordering is now *asserted* via `asks_before_pause == Some(0)` (Q1), not
merely argued from fixture structure; (c) stepped-vs-driven decision sequences match across that
composition, with the log comparison's integrity guarded by the Q2 assertion; (d) the fixture
really pauses (probe evidence). Not pinned by this test alone: choices *before* a pause in other
fixtures (none exist in these arenas today), and the helper's bookkeeping content (P3, M07-022
evidence — `a_driven_combat_continues_after_its_barrage_scoring_pause` validates that).
