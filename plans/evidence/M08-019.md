### Bisect: which categories' file order is load-bearing

Each category reversed individually (28 single-category corpora), same seed, all fields except

```text
planets: DIVERGES        technologies: DIVERGES
all other 26 categories: same
```

### Mechanism identification

**(a) `researchable()` — file order where the oracle sorted.**
`crates/ti4-engine/src/technology.rs:793`: doc comment promises "a stable order"; implementation
iterates `content.records(ContentType::Technologies)` in **technologies.json file order**. The
oracle (pinned `37061c5`, read-only) sorted:

```python
def researchable(game, player):
    return tuple(sorted(a for a in catalogue() if can_research(game, player, a)))
```

Consumers build choice options directly from this order: `strategy_cards.rs:236` and `:278`
("research a technology" — every research opportunity), `action_cards.rs:1096` (Focused
Research). The authored bot samples positionally on tied scores, so option order changes choices.

**(b) `annexable()` — planets in file order where the oracle used system-record order.**
`crates/ti4-engine/src/faction_abilities.rs` (~line 486, Xxcha Peace Accords): iterates
`galaxy::planets_in(...)` = **planets.json file order** filtered by system. The oracle (pinned
`37061c5`, `engine/faction_abilities/xxcha.py:55`) iterated the **system record's own
`planets` array**. Corpus measurement: for **13 of 231 systems** the two orderings differ
(e.g. system `09`: record `[maaluuk, druua]` vs file order `[druaa, maaluuk]`).

### Non-dependencies verified (negative results)

- Deck construction sorts IDs before shuffling (`deck.rs::ids`) — file-order-independent despite
  the loader module doc's stale claim that reordering changes seeded games via deck building.
- `ContentStore::strategy_cards()` (file-order tie-break on initiative) has **no production
  consumers** (grep-verified); initiative ties exist in the corpus (2→2, 4→3, 6→2 cards) but
  never reach gameplay through that accessor — consistent with the bisect (`strategy_cards: same`).
- All other record accessors on choice paths are keyed lookups or BTreeMap/BTreeSet iterations.

### Methodology note (recorded for future campaigns)

`GameResult` contains `seconds: f64` (wall time). Whole-struct `==` between runs therefore always
reports divergence. The first perturbation run compared whole structs and falsely reported "all 28
categories diverge"; the corrected field-wise comparison found exactly two. Any future
equivalence check must exclude `seconds`.

## Resolution of F-M08-019-1 (Option A, implemented in-package)

Operator disposition 2026-08-23: "keep working on the actual project; reviews handled by the
Claude loop" — read as adopting the implementer's recommendation. Finding-specific writable paths
declared in `plans/M08-019_OPEN_REVIEW_ITEMS.md` before any source edit.

**Fix (a) — `researchable()` canonical order.** `crates/ti4-engine/src/technology.rs`: result is
now sorted by `TechnologyId` (derived `Ord`, lexicographic), restoring the oracle's `sorted(...)`
and making the "stable order" doc comment true in the canonical sense. Doc updated to state that
option order must not follow corpus extraction order.

**Fix (b) — `annexable()` system-record planet order.** `crates/ti4-engine/src/faction_abilities.rs`:
each reachable system's planets are now iterated from the **system record's own `planets`
array** (`store.get(ContentType::Systems, …).strings("planets")`) instead of
`galaxy::planets_in` (planets.json file order filtered by tileId), restoring the oracle's
iteration. Candidate sets are provably unchanged: system-record lists and tileId membership agree
on all 231 systems (measured); only orders differ.

**Red-first tests (both verified RED before the fix, GREEN after):**
- `researchable_offers_options_in_canonical_sorted_order` (technology.rs) — asserts the output
  equals its own sorted form; fails under file order because technologies.json is not alias-sorted.
- `peace_accords_candidates_follow_the_system_record_planet_order`
  (faction_abilities.rs) — system 110 prints `[horizon, elnath, luthieniv]` but in planets.json
  file order elnath precedes horizon; with luthieniv controlled the two empty candidates swap
  relative position between old and new code.

**Campaign extension (M08-018 nested-window test).** The fix changed bot trajectories, and the
test's non-vacuity clause (`re_offers > 0`) failed: a mid-window scorer re-offer is rare —
measured **exactly one occurrence in all thirty pre-fix games** (seed 7785 rot 0), zero post-fix.
The engine-level nested-window pins (M07-019/022/023, M08-018 focused tests) all still pass —
this is rare-event sampling, not a mechanism regression. Resolution: the campaign now also plays
six seeds verified under the new ordering to produce at least one re-offer each
(`NESTED_WINDOW_SEEDS = [7_796, 7_801, 7_818, 7_820, 7_849, 7_857]`, found by a temporary sweep
probe over offsets 10..150 × 3 rotations: 15 (seed, rotation) pairs with re_offers ≥ 1). The base
ten-seed set is unchanged; the test's legality/redaction/replay assertions now cover 48 games.
Test runtime ~90 s → ~145 s. Deterministic by construction — same tree, same seeds, same choices
forever.

**Re-baseline (M08-021 v2).** Recorded in `plans/evidence/M08-021.md` with old/new bounds side by
side at full precision; semantic cause stated; protocol constants unchanged. The gate's integrity
check recomputed every bound from current data and asserted bit-equality — transcription verified
by the suite itself.
