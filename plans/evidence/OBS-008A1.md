## Result

1. **Engine.** `tactical::activation_options` attaches `Preview::certain` with a single
   `Quantity::TacticTokens` delta `t → t-1` to every option, where `t` is the seat's current
   tactic pool. It mirrors `activate()`, which spends one tactic token unconditionally (LRR 89.1) —
   the preview asserts only what the engine does. Previews are `#[serde(skip)]`: no option ID,
   label, legal set, payload, replay script, or decision hash (V1 or V2) moves. No `DecisionContext`
   field is added or changed.
2. **Policy.** `tactical_decision_features(choice, option, features)` runs alongside
   `payment_decision_features` / `production_decision_features`. Guarded on
   `choice.context.subtype ∈ {activate_system, movement_step}`, it emits under the new `tactical`
   family:
   - `tactical:subtype:{subtype}` — read from the typed context, never the prompt.
   - `tactical:option-count` — legal option count, `count_value`-clipped.
   - `tactical:optional` — `1.0` when the context marks the decision declinable (absent today; the
     movement context is not yet flagged — that is deferred so this slice cannot move a V2 hash).
   - `tactical:target-system` — `1.0` when the context target names a system.
   - `tactical:preview-known` + `tactical:tactic-tokens-{before,after,change}` from a `Certain`
     outcome naming `TacticTokens`; `tactical:preview-unknown` / `-unavailable` markers otherwise.
   A missing preview and a non-informative outcome emit no numeric fact; a computed-zero `after` is
   a dropped sparse entry distinguished by `preview-known`, exactly as `pay`/`production` do.
3. **Vocabulary.** `tactical` forces `OOV_REGISTRY_VERSION` 6 → 7. `OOV_FAMILIES_V7` is
   `OOV_FAMILIES_V6` with `tactical` appended at index 43; every earlier reserved column keeps its
   index. New pinned fingerprint
   `8643598ee52f0d3b4911c620d86b9b33e0d639c70d1571c4acd62bba68d8f931`. The one-version-back
   inference window moves to v6; v5 is now refused exactly as v4/v3/v2.
4. **Projection.** `tactical` is `Transferable`: subtype, count, and a bounded command-token pool
   delta each mean the same thing in any game.

## Focused evidence

- `tactical.rs::obs008a1_activation_options_preview_the_exact_tactic_token_spend`: with a pool of
  4, every option previews `Certain { TacticTokens: 4 → 3 }`; the preview is then checked against
  actually calling `activate()` and re-measuring (`3`); option IDs and the label are unchanged.
- `tactical.rs::obs008a1_no_activation_choice_means_no_preview_to_get_wrong`: a zero pool is still
  not offered the action, so the preview never describes an activation from empty.
- `features.rs::obs008a1_tactical_features_carry_subtype_count_and_exact_token_consequence`:
  `tactical:subtype:activate_system`, `tactical:option-count` (2), `tactical:target-system`, and
  exact `tactical:tactic-tokens-before/after/change` (4 / 3 / -1) are present; a pool of 1 → 0
  drops `tactic-tokens-after` (sparse zero) while keeping `preview-known`; a `None` preview emits
  the subtype but no numeric fact; a `produce` choice emits no `tactical:*`; the facts survive
  `mlp_option_features` and `projection::admits`.
- `vocabulary.rs::the_reserved_order_is_pinned_…`: v6 → v7 append block and the pinned v7
  fingerprint; `version_six_loads_for_inference_without_renumbering_its_columns` and
  `version_five_remains_refused_for_inference` replace the v5/v4 pair.
