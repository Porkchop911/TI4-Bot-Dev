## Integrity failure

The post-batch oracle guard found an untracked directory:

```text
?? Projectsti4-engine-rs.tmp-m00-011/
```

at `D:\Projects\ti4-engine\Projectsti4-engine-rs.tmp-m00-011` — 816 entries, 100 MB, all of them
pytest `tmp_path` directories named after the tests that created them. No tracked oracle file
changed, but the guard requires a clean worktree, so oracle-dependent work stopped.

### Root cause

Not a pytest path-reinterpretation. **The shell removed the backslashes before pytest ever saw the
argument.** The override was passed unquoted to a Bash-family shell, where `\P`, `\t` and `\.` are
escape sequences, so the process received a path with no separators at all. Reproduced directly:

```console
$ python -c "import sys; print(repr(sys.argv[1]))" --basetemp=D:\Projects\ti4-engine-rs\.tmp-m00-011
'--basetemp=D:Projectsti4-engine-rs.tmp-m00-011'

$ python -c "import sys; print(repr(sys.argv[1]))" --basetemp=D:/Projects/ti4-engine-rs/.tmp-m00-011
'--basetemp=D:/Projects/ti4-engine-rs/.tmp-m00-011'
```

`D:Projectsti4-engine-rs.tmp-m00-011` is a *drive-relative* Windows path — `D:` with no leading
separator means "relative to the current directory on drive D:", which was the oracle. Hence the
directory landed inside `D:\Projects\ti4-engine` with the separators visibly missing from its name.

The name is the evidence: had pytest mishandled an intact Windows path, the backslashes would still
be present in it.

### Fix for recurrence

Pass the override with **forward slashes**: `--basetemp=D:/Projects/ti4-engine-rs/.tmp-m00-011`.
Windows Python accepts them, and no shell in this environment treats them as escapes — so the
argument survives both Bash and PowerShell without quoting discipline having to be remembered.
Quoting the Windows form works too, but only as long as every future invocation remembers to quote;
forward slashes are correct by construction.

## Resolution — 2026-08-12

The owner authorized removal of this exact directory. Rather than delete 100 MB, the tree was
**moved to where the override had intended to put it**: same drive, so an instantaneous rename, and
no data destroyed.

```console
$ mv "/d/Projects/ti4-engine/Projectsti4-engine-rs.tmp-m00-011" \
     "/d/Projects/ti4-engine-rs/.tmp-m00-011/basetemp-recovered"
```

The destination is inside the package's own gitignored scratch directory (`.gitignore:26`), so it
neither enters this repository's history nor leaves anything for a future guard to trip on. All 816
entries verified present after the move.

Verification, oracle:

```console
$ git status --porcelain          # (no output — clean)
$ git rev-parse HEAD              # 37061c511a4780d4c0719e0342533a498cd4b457
$ git rev-parse --abbrev-ref HEAD # codex/fully-learned-policy
$ git diff --stat; git diff --cached --stat   # (no output — tracked tree pristine)
```

Every ignored cache in the oracle (`.pytest_cache`, `.pytest_tmp`, `.ruff_cache`, `.coverage`, and
each `__pycache__`) carries an mtime of 2026-08-11 or earlier, so `PYTHONDONTWRITEBYTECODE=1` and
the disabled cache provider did hold. The stray basetemp was the run's only escape.
