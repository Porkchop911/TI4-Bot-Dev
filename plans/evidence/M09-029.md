# M09-029 — CPU MLP game/throughput gate

**Milestone row:** M09-029. **Normative:** `docs/MLP_PLAN.md` revision 5 §7.1.
**Author:** Claude Opus 5 — not eligible to review. **Review tier:** D.
**Permission class:** P2 (measurement).
**Harness:** `crates/ti4-mlp/examples/cpu_gate.rs`, `crates/ti4-mlp/examples/forward_profile.rs`.

## Headline

**The gate's own metric and a direct measurement of the same system disagree, and the reason is
measured rather than argued.**

| | width 256 | width 128 |
|---|---|---|
| §7.1 shadow ratio (the specified metric) | **2.888×** | **2.716×** |
| MLP actually deciding, per decision | **1.681×** | **1.586×** |

Workload: 16 seeds × 6 rotations, 4 rounds, training pool, 5 warm-ups, 20 alternating timed batches,
32,306 decisions per batch. Raw per-sample times are printed by the harness.

## Why the two disagree

§7.1's shadow arm has the linear champion choose while the MLP scores the same legal set and
discards the result, so both arms play identical games. Its stated premise is that **"the tiny
linear lookup remains in both arms"**.

On this codebase that premise is false. The linear bot's per-decision work is not a lookup — it is
the same schema-4 feature extraction the MLP needs. The shadow arm therefore performs that
extraction **twice**, and charges the difference to the model.

Measured decomposition, each component isolated by its own probe (linear baseline 1.891 s):

| arm | median | marginal | per decision |
|---|---|---|---|
| linear | 1.891 s | — | — |
| + raw schema-4 extraction only | 2.898 s | 1.007 s | 31 µs |
| + MLP projection and sparse conversion | 3.265 s | 0.367 s | 11 µs |
| + policy model (W256) | 4.529 s | 1.264 s | 39 µs |
| + critic | 5.525 s | 0.996 s | 31 µs |

**Raw extraction alone, with not one tensor operation executed, is already 1.53×.** A model that
cost literally nothing would still measure 1.53× on this metric, leaving 0.47× of the 2.0× band for
the entire MLP. The shadow ratio is not a measurement of the architecture here.

So the harness adds a third arm in which **the MLP itself decides**. That plays different games,
which is exactly what §7.1 avoids by timing whole batches — so it is compared **per decision**,
which is immune to the trajectories differing. It is also the row's required legality smoke: every
game completes with the MLP choosing, or the batch refuses.

## What the profiling changed, and what it found

Three optimisations, each measured before and after. The first two were guesses, and are recorded as
guesses; only after building `forward_profile.rs` did measurement drive the work.

| change | shadow ratio, W256 |
|---|---|
| as implemented at the start of M09-029 | 3.816× |
| keyed vocabulary lookup (`column_of_key`) | 3.601× |
| memoised admission (`admits_key`) | 3.337× |
| naive batched gather via `index_add` — **made it worse** | 4.124× |
| deduplicated gather | **2.888×** |

**The gather is the decision.** At realistic shape the per-option gather was 57.4 µs, more than
everything else in the forward pass combined. It is **latency**-bound, not FLOP-bound: the input
table is `[16384, width]`, far larger than L2, and each decision fetched hundreds of 1 KiB rows from
random offsets. Halving the trunk width barely moved the total, which is the signature of a per-row
cost rather than a per-byte or per-FLOP one.

So the lever is row count. Measured over 40,000 real decisions: **6.2 options, 528.8 gathered rows,
of which only 131.9 are distinct** — every row fetched about four times, once per option that
mentions it. `gather_reduce_batch` now gathers each distinct row once into a cache-resident
`[distinct, width]` block and combines it with one `[options, distinct] × [distinct, width]` matmul.
That is §4.3's "aggregate duplicate feature names first", which was specified and not implemented.

Determinism is preserved: duplicates *within* an option are still aggregated in the fixed
`ordered_pairs` order F-M09-025-3 established, and M09-026's dense-reference tests for duplicates,
negatives, fractional values, OOVs, empty vectors and maximum option batches pass unchanged.

## A defect in my own harness, found late

The first version fingerprinted `seat.trajectory` from the rollout result to assert the two arms
played identical games. **`play_with_deciders` populates trajectories only for the `LearnedBot`s it
constructs itself**, and this gate passes its own deciders in — so the trajectories were empty, the
fingerprint hashed nothing, and the arm-for-arm identity assertion could not have failed. It
surfaced only because the MLP arm needed a decision count and reported zero.

Decisions are now recorded at the decider, in every arm. The fingerprints match with real data.

The diagnostic probes (`SKIP_MODEL`, `SKIP_CRITIC`, `SKIP_PROJECT`, `SHAPE`) are kept, because the
decomposition above has to be reproducible — but a run with any of them set now refuses to print a
verdict, since it is measuring something other than the gate.

## Verdict, and what I did with it

By §7.1's bands applied to the shadow ratio: 2.888× at width 256 is in the fallback band, and the
prescribed width-128 rerun gives 2.716×, still above 2× — so **the literal verdict is STOP for
architecture review**.

By direct measurement of a real MLP rollout: **1.681× at width 256**, inside the band.

I am not entitled to overrule a gate by preferring my own metric, so both are recorded and the
recommendation is stated rather than acted on: **accept width 256 on the direct measurement**, on
the measured ground that the shadow metric's 1.53× floor makes its 2× band unreachable on this
codebase regardless of what the model costs. That is a question for the architecture review §7.1
calls for.

Work continued past this point to M10-031 on the operator's instruction of 2026-08-26 ("keep going
until training runs … review can be done later"). The STOP is recorded, not resolved.
