## Decision and rationale

**Option A implemented:** `Player::PartialEq` now compares `event_feats`. Rationale recorded at the
site: feat evidence gates secret-scoring eligibility, so a direct-vs-stepped divergence in feat
evidence must fail state equality even when no objective has scored yet. Consistency arguments:

- The rest of the occurrence model is already compared (`GameState.scored_feat_occurrences`,
  `feat_occurrence_seq`); this was the one M06 field left out.
- The `impl PartialEq for Player` doc comment enumerates its deliberate exclusions (the oracle's
  `compare=False` fields: relic_fragments, leaders, assimilated_technologies) — `event_feats` is a
  new Rust-only M06 field that never existed in the oracle and was never listed there.
- The field carries no `// Not compared.` marker of its own.

Option B (documented exclusion with reason) was not chosen: there is no concrete contract the
comparison breaks — the full workspace suite passes with it added, after one test-harness
completion described below.

## Exposed dependence diagnosed (not fixture-regenerated)

The projection change turned one pre-existing engine test red, exactly as the spec anticipated:
`combat::tests::a_stepped_combat_matches_the_driven_one` (`assertion failed:
stepped_state.identical(&driven_state)`). Diagnosis:

- The test compares a manually stepped combat (settle / pending_choice / resolve loop) against the
  synchronous `resolve()`, asserting final-state identity.
- Both real drivers perform post-combat bookkeeping the stepped harness omitted: they snapshot the
  system with `before_combat` before the first die and, at completion, call
  `note_combat_event_feats(state, …, &before, &outcome, window.combat_occurrence())` — see the Game
  driver at game.rs:279–286 and the synchronous API at combat.rs:1489–1495.
- In this fixture (cruiser×3 vs carrier×2), `note_combat_feats_at` records
  `Feat::HeldThreeShipsAfterASpaceCombat` for the side still holding ≥3 non-fighter ships, so the
  driven state carried feat evidence and the stepped one did not. Before this package that
  divergence was invisible precisely because `event_feats` was omitted from equality — the
  detection-latency scenario M2 predicted, now caught by design.

Fix: the stepped branch of that test now mirrors both real drivers (pre-combat snapshot + feat
recording at completion). No assertion changed — the `identical()` comparison stands as written;
both sides of it simply do the same work. This is completing an incomplete simulation, not
weakening a red test or regenerating a fixture.

## Behavior change note

State equality is now stricter: two states differing only in `Player.event_feats` compare unequal.
This can only make equivalence/replay comparisons catch more, never fewer; no serialized format,
choice ID, canonical projection for replay hashes, or registry changed. Downstream VP/clearance
numbers are unaffected (no scoring behavior moved).

## Coverage limit recorded per review N1 — the invariant holds on `event_feats` outside the pause

The reviewer probe-confirmed that the completed harness still stalls on any fight whose round-1
barrage fires a feat: the stepped branch gained `resolve()`'s **feat bookkeeping** but not its
**pause consumption**. `resolve()` loops on `while window.outcome().is_none()` with `drive()`,
`take_scoring_occurrence()`, and `settle_open()` (combat.rs:1478–1487); the harness loops on
`pending_choice`, which returns `None` at `Stage::RollingAfterBarrage` — so a pausing fight leaves
the loop unresolved and the new `.expect("the fight resolved")` panics. The test passes today only
because its fixture (cruiser×3 vs carrier×2) has no fighters and never pauses.

**Corrected claim:** the direct-vs-stepped equivalence invariant now holds on `event_feats`
**for fights that do not pause**. It is verified only outside exactly the M06 paths this package
line exists to protect. This is not a regression introduced here (before M07-021 the test could not
have caught a pause-path divergence either, because feat evidence was invisible to equality), but
the earlier wording that the invariant "holds on the field M06 introduced" is an overstatement and
is corrected by this section.

**Scoped follow-up: M07-022** (prep spec `plans/M07-022_STEPPED_EQUIVALENCE_ACROSS_PAUSES.md`,
milestone-plan row added) — extend the stepped harness with a pausing fixture plus the
`take_scoring_occurrence()` / `settle_open()` consumption loop, so equivalence is verified across
the M06 pause path. Per the reviewer's instruction and the spec's hard ordering constraint, M07-022
is named **before** the M07-020 exit review and is now a dependency of it.

## N2 disposition (author's discretion)

The harness replicates `resolve()` rather than exercising the stepped production consumer at
game.rs:216, so it can only catch drift between copy and original — which is exactly what happened
here. Disposition recorded:

- **Adopted in M07-022:** factor the completion bookkeeping (`before_combat` →
  `note_combat_event_feats` on `combat_occurrence()`) into one helper that both `resolve()` and the
  harness call, so a third drift is structurally impossible. This lands together with the pause-
  consumption loop because that is when the replicated surface grows.
- **Deferred to M07-020's consideration:** re-pointing an equivalence test at `Game` itself (the
  invariant as named). That is a larger design change — Game-level direct-vs-stepped comparison has
  its own fixture and window-pause semantics — and belongs in the exit review's scope decision,
  not in this package. Also noted for that review: the two production consumers deliberately differ
  at the snapshot (`before_combat_with_notes` carrying promissory notes for `baf`, vs plain
  `before_combat`), which a Game-level test would have to account for.
