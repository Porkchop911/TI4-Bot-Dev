## Invariants and compatibility contract

- The exact schema version is serialized into every hash input; a schema revision is an explicit
  code-level version change, never an implicit output change.
- Hashes use SHA-256 over UTF-8 `serde_json` bytes. The fixed envelope field order and the event's
  `BTreeMap` payload make equivalent map construction byte-identical.
- Decision records preserve their offered-option vector order. Sorting it would erase observable
  choice presentation and disagree with the oracle's ordered `Choice.options` list.
- Hashes include event cancellation and IDs and all decision-record fields; pointer addresses,
  allocation order, wall time, and unrepresented game state have no influence.

## Tests to add

3. A fixed decision record has a golden SHA-256 digest; reordering offered options produces a
   distinct digest.

## Implementation and compatibility evidence

- `CanonicalHashVersion::V1` is serialized into an explicit `schema_version` envelope field
  before SHA-256. The constructor is private, so a supported schema bump requires an intentional
  source change rather than caller-selected drift.
- `event_hash` covers all serialized `Event` fields; `decision_hash` covers all serialized
  `DecisionRecord` fields. The hashes carry their generating version alongside the lowercase
  hexadecimal digest.
- Fixed UTF-8 golden values protect the complete byte contract. `BTreeMap` payloads eliminate map
  insertion-order variance; decision option order is retained because it is observable.
