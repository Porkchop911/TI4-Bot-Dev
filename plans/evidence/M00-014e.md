# M00-014e — Fail-closed integrity guard implementation

## Package specification

- **Milestone/package:** M00-014e, implementation split from M00-014c/d; M00-014a/b's real
  manifest generation remains pending a clean oracle.
- **Objective:** Provide a local, read-only guard that rejects a missing/invalid manifest, moved
  commit, dirty worktree, missing file, or changed SHA-256 before migration work trusts the oracle.
- **Permission class:** P1 only for `tools/oracle_integrity_guard.py`, its isolated local test,
  this evidence file, and `plans/EXECUTION_STATE.md`. Test fixtures are temporary Git repositories
  created under the Rust repo; no oracle command is run because its worktree is known dirty.
- **Compatibility class:** security/integrity boundary. The guard is deliberately fail-closed.
- **Explicit non-goals:** generating the real manifest from a dirty oracle, cleaning the oracle,
  automated CI integration, or claiming M00-014 complete.

## Implementation

- `tools/oracle_integrity_guard.py` validates a versioned manifest, normalized relative POSIX paths,
  lowercase SHA-256 digests, pinned commit, clean Git status, presence, and content hash for each
  selected file.
- `tools/test_oracle_integrity_guard.py` creates throwaway Git fixtures under this repository and
  proves clean acceptance plus rejection for dirty worktree, moved commit, and path traversal.
- The default production manifest path is `plans/oracle_integrity_manifest.json`, intentionally
  absent until its values can be generated from the restored clean pinned oracle.

## Manifest generation

`tools/generate_oracle_manifest.py` writes what the guard verifies. It refuses to run against an
oracle that is dirty or off the pin, so a manifest can never record hashes of files that were not
the pinned ones, and it re-checks commit and cleanliness *after* hashing so a long pass cannot
straddle a change to the tree.

**Selection — 238 files:** `engine/`, `bridge/`, `tests/`, `data/`, `configs/`, and
`pyproject.toml`. That is what the migration ports, the suite that specifies its behaviour, and the
configuration that pins its dependencies.

Excluded: `docs/`, `out/`, `tts/`, `tools/`, and the repository dotfiles. None define engine
behaviour, and a guard that fails on an unrelated documentation edit would train its readers to
bypass it.

Note what the per-file hashes are actually for. The commit and cleanliness checks already imply
tracked content, since any change to a tracked file implies a different commit. The digests are
defence in depth against tampering *below* Git — a rewritten object or a swapped worktree — which
is why they are pinned in this repository rather than read from the oracle's own history.
