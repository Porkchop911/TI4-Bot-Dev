# web2: online play

Part of `web2/AGENTS.md`: the Patterns and the rules of Screen size and Text there apply here too.

## Online play

- `/` is the start screen (`src/dev/StartApp.tsx`): two rows, "Single player" and "Multiplayer", each the control, with the keys 1 and 2, and the name of the player (`ti4.nickname`). A row is a page load. "Multiplayer" loads `?online`, "Single player" loads `?single`, the setup of a new table (the Lobby section of `lobby.md`, "Single player"). Under them is the list of the saved games of the browser (the save list in `local-play.md`).
- `?online` makes a table on the server and goes to `?online=<game_id>&seat=<player_id>`; that address is the table, its game, and the player of the tab (`src/dev/OnlineApp.tsx`). While the table is a lobby the page is the lobby (the Lobby section of `lobby.md`); when the table says that the game runs, the page is the game. The server draws the faction of every seat and the speaker from the seed, and plays the strategy cards of Thunder's Edge (`te`) when the table names no set: the page is any faction, and it is not always asked first. The plans are `plans/2026-10-11-ONLINE_MULTIPLAYER_PLAN.md` and `plans/2026-10-12-LOBBY_PLAN.md`.
- The address that makes a table can name its seats, its seed, the nickname, the map and the wait of the seats that the server plays: `?online&players=6&seed=3&name=Ada&map=random&wait=1` (`src/dev/onlineStart.ts`). `map` is a map of the server by its alias, or "random"; `wait` is in seconds, 0 to 30. Without `players` the table has the seats that the host of this browser chose last, else four; without `name`, the name of the start screen. No page has a control for the map yet. The address of the table has none of it, so a reload is the table and makes no other one.
- The quick start is `?online&fill=random`: a game of eight, the page has one seat, the other seats decide at random, and the game starts at once. The row "Multiplayer" of the Dev sheet of a local game and the e2e use it. With `&wait=1` the other seats take a second for each answer.
- While a seat that the server plays takes its time, the server says who the game waits for and nothing else (`turn_status`). The transport tells it as a `status` event, not as an update, so what is staged stays; the toolbar says "Waiting for Rule bot 1" (the name of the player of the seat), and "Waiting for reactions" while a reaction window is open (it names no seat: who can react is private).
- The way out of a table or its game is the header link "Start", to `/` (on a phone the last item of "Reference and more" in the game), as in a local game.
- A reload goes on as the player of the address. A game that the server does not have (it was deleted, or the address is wrong) is said in place of the game: "The server no longer knows this game.", with "Start" in the header. The page does not try again. A server that cannot be reached is not such a game: the page keeps trying.
- The server is at the address of the page: `/api` and `/ws` (the HTTP calls of a table in `web-shared/src/net/api.ts`), through the proxy of `vite.config.ts` in development (the port is `TI4_E2E_BACKEND_PORT`, 8080 by default). Start it with `cargo b-web && target/debug/server`.
- The page is the same code as in a local game: `src/session/wsTransport.ts` is `messageTransport` (`src/session/messageTransport.ts`, the transport of a local game too) over `socketLink` of `web-shared/src/link/`. Nothing in `game/`, `ui/` or `useLiveSession` asks which transport it has. A game on the server has no capability, so it has no Dev sheet. The socket of a game (`socketLink`) and the socket of a table (`table.ts`) are `connect` of `web-shared/src/net/socket.ts`, the module shared with web/ (`web-shared/AGENTS.md`): it opens a lost socket again after a backoff (0.5 s, doubled, up to 15 s), and sends a heartbeat every 10 s while it is open.
- Undo online is the undo of the seat. The button is shown exactly when the server says that the seat may take its last decision back (`can_undo` of the update): the decision is its own, the game waits for the seat, and since the decision nothing hidden was shown (a card that was drawn, an exploration, a hand that was looked at), nothing was rolled or shuffled, and no other seat decided. So it does not go back past such a point, and a local game does (it is a tool for testing). One undo takes back what one undo of a local game takes back: one answer, or a movement, the landings or a purchase whole, staged again as it was sent. A window that is declined for a Never card goes with the answer before it. The server plays the game again without the decision and closes the socket as replaced; that is not shown as offline. An undo that the server refuses is a toast that names the barrier. The undo of the host (the event log, restore, redo) is not in web2.
- A lost connection has one signal (pattern 6): the status of the toolbar says "Offline · reconnecting". The game stays in view, no choice is open, and the page tries again by itself. It is not an error.
- An answer that the server did not take is a toast with the reason, and the same choice is open again. It is never silent.
- The printed cards are those of the engine of the page, also online. The page refuses a server with another corpus or another protocol, with both versions in the text.
- **A seat for each tab.** `localStorage` is shared by all tabs, so the address says which player a tab is (`&seat=<player_id>`; the id is public, the credential is not in the address). The browser keeps every player that it has in a game (`ti4.online.<game_id>.players`: the id and its player session), so two tabs of one browser can be two seats. A tab without `seat` is the one player of this browser in the game; with none it is a visitor; with several the lobby marks them "(yours)" and a row makes the tab that player. The key of an older page (`ti4.online.<game_id>.session`) is moved to its player once. The Never cards are kept by the server.
- **What a seat staged is kept by the server** (owner, 2026-10-14; `plans/2026-10-14-SAME_SEAT_TABS_AND_ONE_DOMAIN_PLAN.md`, phase 2): the staged movement, landings and production, the private draft of a tactical action with its undo, and the draft of a secondary. It is the same in every tab and on every device of the seat, and a change in one tab is staged in the others at once. What is open on the screen is of each tab: the workspace (Live or Draft), the step of the draft in view, a sheet, the pane, the marks that the player set by hand. `SeatStore` (`src/session/seatStore.ts`) is the seam: `Transport.staged`, online and in a local game alike (`seat_staged` and `put_staged` of the protocol; the transport waits a moment for the next change, has one write of a slot on its way at a time, and takes a newer value of the server over its own). In a local game and in single player the engine keeps it in the saved game (the Local play section of `local-play.md`). What an older page kept in `localStorage` (`onlineKeys`) is put once, when the server has nothing for the seat, and then removed. A draft that is larger than a slot of the server (48 KiB) loses its oldest undo states first.
- **One sender for the answers of a seat** (phase 3 of the plan). Two tabs of one seat can both answer the same question; the server takes the first, and tells the other `answered_elsewhere`. That is no error: the transport shows no toast and does not ask for the game again, and the update that follows shows the answer. (A page that did not ask for the staged work, web, is told `stale_nonce`.)
- **A ready draft of a secondary is sent by the server**, once for every tab and device of the seat, also when none is open: when the game asks the seat, and when the seat marks the draft ready while the game asks it. The server checks it as the page did (`run_draft` with the scope, played whole), and the seat is not asked. A draft that is sent is cleared; one that no longer fits is written back not ready, by the server, and every tab says "Your draft no longer fits the game. It is not ready." (`SeatStore.subscribe` tells a write of the server apart). The page sends no ready draft and does not hold the question back: when the game asks the seat, the game did not send. The engine of a local game sends it the same way (`ti4_host::staged::ready`). "Send draft" of a draft that is not ready is still sent by the page.
