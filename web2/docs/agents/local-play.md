# web2: local play, transport, drafts, saved game

Part of `web2/AGENTS.md`: the Patterns and the rules of Screen size and Text there apply here too.

## Local play

- `?local=<seed>&players=8&humans=<mask>` plays a real game of the engine in the page (`src/dev/LocalApp.tsx`). Build the engine first: `scripts/build-wasm.sh`.
- "Single player" of the start screen is `?single`: the setup of a table in the page; its game is `?single=<id>` (the Lobby section of `lobby.md`). `?local=…` and `?scenario=…` stay the games of a fixed setup, for tests and for the tools of the Dev sheet. `DEFAULT_GAME` (seed 42, 8 seats, seat A played here; `src/dev/defaultGame.ts`) is the setup of a `?scenario=…` that names no other. `?save=<id>` is a saved game that has no address of a setup (an imported game, a game of web/; `src/dev/SavedApp.tsx`): the save says which game it is. The installed app opens `/`, the start screen. `?gallery` is the gallery of the primitives.
- If the engine of a local game does not load (missing file, or no JSPI), the page says so with the reason ("Local game unavailable.", "Single player unavailable.").
- The header has the way out of the game: "Start", to `/`. On desktop it is a button after the reference sheets; on a phone it is the last item of "Reference and more". A page load, not a game choice.
- A local game has no bar at the bottom. "Dev" (a header button on desktop; the item after "Start" in "Reference and more" on a phone) opens the Dev sheet, which is a reference sheet: the seed, the seats, the saved answers, the other seats, "Play as", "Start from", New game, Export and Import. It was "Settings" until 2026-10-10: everything in it is for testing. Without the shell (loading, a saved game of another engine, a notice) the page has a row with only "Dev".
- "Start from" is one list: "Round 1" and the scenarios of the engine (`crates/ti4-host/src/view/scenario/`, the same list as the server's `/api/dev/scenarios`). A row is the control and loads the page at the address of that game (`?scenario=<id>&humans=<mask>`); what a scenario holds is behind "?". A scenario is a game of its own: the engine sets up its board (the late games on their seed, the scenarios of three seats on seed 42), and it is saved under its own slot, so a reload, an undo and New game work as in any game. Most scenarios of three seats have an opening: the engine answers seat A up to the question of the scenario (the research, the production, the first retreat of a battle, the first question of an invasion) before the page is asked, when the page plays seat A, as the server does after a launch. The answers are ordinary decisions of the save, and an undo takes them back. A new case for testing is added to a scenario in Rust, with a test that the facts show it. A new feature gets its cases in the late-game scenarios when it can (owner, 2026-10-11), so that it is seen in a full game and not in round 1 only: every state that its screen shows, at every seat. Example: for the Secrets sheet every seat has three secret objectives, some scored, some that are scored in the action phase and some of the other phases.
- `src/session/` turns an update of the game into the view models. It imports `model` only, and it decides no rule: a value that needs a rule comes from the engine.
- The page does not know where the game runs. `Transport` (`src/session/transport.ts`) is the seam: an update, an answer, a script that is run, a plan or a draft that is sent, the mode of a card, an undo. A tool for testing a local game (Step, "Play as", the scenarios, the saved game) is a capability of the transport (`Transport.capabilities`, `GameSession.capabilities`): the Dev entry and each part of the Dev sheet are shown from it, never from the kind of game. How a plan answers a question of the game is decided in Rust (`script_answer` in `ti4-host`), on both hosts. Both kinds of game are one transport, `messageTransport(link, …)` (`src/session/messageTransport.ts`), over a link of `web-shared/src/link/`: online `socketLink` (`wsTransport.ts`), in a local game `engineLink` (`wasmTransport.ts`). The engine of a local game runs in a Web Worker (`web-shared/src/engine/worker.ts`), so the main thread of the page does not play the game, and it speaks the protocol of the server (`ClientMessage` in, `ServerMessage` out). The capabilities of a local game are local commands of the engine: Step and the wait are `step` and `stepping`, "Play as" is `switch_seat`, the saved game is `save_state`. The questions that need no game (the setup of a table, the scenarios, the catalog) are asked of an instance of the engine on the main thread. The space odds of a local game are a query of the Worker (`spaceOdds(link.query, …)` of `web-shared/src/engine/odds.ts`), which asks the instance of the running game; an online game asks one instance of the engine on the main thread (`pageQuery`).
- A decision without a dedicated screen is one list in the action panel.
- The activation and the movement of a tactical action use the screens of these steps. In the movement the systems that ships can leave are the choice on the board, so a phone stays on the map. The facts come from the engine with the update (`tactical`), and "Move fleet" sends the staged movement as one plan (`Transport.submitPlan`). A plan that the game refuses is taken back whole; one undo takes a movement back whole, and it is staged again as it was sent, so the player can change a part of it. The check marks that the player set by hand are not kept.
- The landings of an invasion use the screen of that step too (the Invasion section of `tactical.md`). The facts are the third kind of `tactical`, and "Commit ground forces" sends the staged landings as one plan, with the rules of a movement plan: refused whole, stopped by another decision with the rest staged again, and taken back whole by one undo. The staged landings are kept for a reload as the staged movement is. After the last unit the game does not ask for the end of the landings, so the plan needs no answer for it.
- The production uses the screen of that step too (the Production section of `tactical.md`). The facts are the fourth kind of `tactical` (`ProductionFacts`): every unit of a production with its price, its places, its supply and its printed values, and why the seat cannot produce it when it cannot, the limits, the discount, and the planets and trade goods that pay. "Produce units" sends the build and its payment as one plan, with the rules of a movement plan. The game asks for a payment after each purchase; the plan answers with the staged payments in their order, whenever it is asked, and leaves out what the game did not need. A build whose payment does not cover it is refused whole. The staged production is kept for a reload.
- The limits of a staged production are sums over the facts: the fleet pool and the capacity do not count what a rule excuses (fighters at a space dock, Fighter II). The game has the last word when the plan is sent.
- The Draft tab opens the private draft of a tactical action: its activation, its movement, its landings and its production, on the screens of these steps (pattern 10). A draft is a script (`src/session/draft.ts`): the tactical action, its system, then the steps of its movement, of its landings and of its production. The engine plays the script as the next turn of the seat on a copy of the game, each time the draft or the game changes (`Transport.draft`), and the screens are made from where that run ended. The answer comes later than the question (a `draft` event), also in a local game: until it is there, the screen is of the draft before and its main button waits. A change of the game alone (another seat acted) does not make it wait: the screen and what is staged stay, and the answer for the new game replaces it. What is staged is cleared only by a new question of the viewer (`fresh` in `useLiveSession.ts`), in Live and in both drafts. Nothing of it is in the game or in its saved decisions.
- The draft opens whenever the page waits in the strategy phase or the action phase and the seat has not passed; the tab says why when it does not. In the strategy phase it is the draft of the turn that comes (owner, 2026-10-10). At the turn menu the Tactical row of the picker opens the draft, and so does "Activate this system" of the inspector, with that system staged (the Action picker section of `decisions.md`); "Apply to Live" is the way a tactical action is played. Undo of the system in Live opens the activation in Live again.
- In the draft, "Activate system" records the system, and every change of the movement is recorded at once (the Movement section of `tactical.md`). The recorded activation opens for an edit (the Activation section of `tactical.md`): while it is open the game is asked for the action only, at the choice of a system, and another system replaces the activation with the later steps kept (`reactivate` in `draft.ts`). Undo and Redo of the toolbar go through the states of the draft; "Start over" and "Discard draft" are in its menu. The draft and its history are kept (`SeatStore`, slot "plan": the engine in its saved game in a local game, the server online), so a reload keeps them.
- "Apply to Live" is enabled at the turn menu of the seat, when the game played the whole draft. Its dialog says what is sent. It sends the action, the system and the movement as one request (`Transport.applyDraft`): refused whole, or stopped by another decision, as a movement plan is. The draft is then gone.
- A draft that the game no longer plays (the system got a command token, a ship is gone) keeps its script, and Apply is disabled. The refusal of the engine names the entry (`DraftStop::Refused`: `entry` and `code`; `reviewOf` in `draft.ts`). Its step has the tab "Needs review" (the chip "!"; while the step is in view the pill says it), and a marked row above the step's content: "✗", the entry by the names of the units and the board, and why (`select/review.ts`). The footer says what to do. Remove takes the entry out with what it brings (a ship with its hold, a purchase with its place and payment; a step that the action ends before goes whole), as one step of undo (`removeEntry`); a change of the step does it too. The activation is fixed by "Edit activation", a payment by a change of the payment.
- The draft goes on as far as the game is certain: from the movement to the landings and to the production. A step that is not drafted is decided in Live. A step in view stays in view while it is changed; its main button goes on. The tabs open every step that the game came to with the draft. A change of an earlier step keeps the later steps, and the game checks them again.
- The draft ends where something random lies ahead: a roll (a gravity rift, space cannon, a combat), a card that is drawn (a landing on a planet that nobody explored), ships of another seat in the system. The footer says so, and the step where it ends has the pill "Preview ends here". This ends the check of the draft, not the draft: Apply stays possible, and the game goes on in Live. Apply sends the steps that the game played; what the draft holds after that point is staged again in Live when its step opens, and nothing of it is sent.
- A production of a draft is in the draft when it is paid. Until then the build is kept, the footer says so, and the game is not asked for it.
- What an ability of the seat asks before a step (AI Development Algorithm) is a list in the draft too. Its main button is "Record": the answer is a part of the draft.
- The game asks "negotiate, or continue" between the steps of a tactical action when the seat has a neighbour. A plan that still has steps continues; so does a draft.
- The Dev sheet has the row "Multiplayer", after "Start from". It loads the address of the quick start, on the seed of the page (`?online&fill=random&seed=<seed>`; the Online play section of `online.md`). The row says the seed and the seats; what it does is behind "?". A page load, not a game choice: the local game stays saved under its own address.
- The Dev sheet has "Other seats": Run (the default) or Step. With Step the engine waits before each decision of a seat that is not played here (the `ask` of the engine has `waiting`, and nothing of that seat is decided yet); the panel names the seat, and the main button "Step" lets it decide (the local command `step`). The seats decide the same either way, so the saved game does not change. The setting is of the page (`STEPPING_KEY`), for testing: a draft can be opened while another seat has the turn. A reload plays the saved decisions again and then waits at the same step.
- The Dev sheet has "Play as": one row for each seat, with "✓ Playing" or "Random". A row of a random seat is the control: that seat is played here from now on, and the seat that the page was shown as decides at random, from its open decision on (`Transport.capabilities.switchSeat`). With a mask of several seats only the shown seat is given up. The engine drops what the seat that is left staged. Undo does not go back before the change: to play the old seat again, choose it (owner, 2026-10-10). The changes are part of the saved game (`switches`: the number of the decision and the seats), so a reload, Export and Import keep them.
- In local play the game decides when a ship uses Gravity Drive: only when the ship cannot arrive without it. The toggle is then on and locked. The free toggle of the Movement section of `tactical.md` is not offered there.
- The draft of a secondary (the Strategy cards section of `strategy-cards.md`) is a script too: the answers by their ids (`src/session/secondaryDraft.ts`). The engine plays it with the scope of the secondary (`Transport.draft(script, scope)`). It is kept as the draft of a tactical action is (slot "secondary"), and a ready draft is sent by the engine when the game asks the seat, as the server sends it online (`ti4_host::staged::ready`). In a local game the page is shown the game only when a seat of the page is asked, so a secondary is drafted before the seat is reached only with "Other seats: Step", or with several seats played here. A reload goes on at the same decision of the game.
- The game is saved as the server keeps a game (owner, 2026-10-13): its seed, and the option id of every decision of every seat, in order, with the table that the game was set up as. The save is the one of the engine (the `save_state` of `HostSession`, format 2: `game`, `decisions`, `answers`, `switches`, `staged`), written at each question of the page. A reload plays it again from the seed: the engine is given each saved decision, whoever the seat is, so no bot decides again and no seat waits, and the game goes on where it was. An undo goes back through the checkpoints of the engine, or the engine plays the game again with its decisions cut at the answer that it takes back, with what the other seats decided after it. The answers that it may take back are kept by the track of the server's undo with the local rules (`ti4_host::planning::undo`, `UndoRules::Local`): only a change of the seats cuts it, not a die, a shuffle or another seat. The Dev sheet says both counts ("3 answers saved · 57 decisions of all seats").
- **Where it is kept: the save store of `web-shared/src/storage/`** (IndexedDB `ti4-offline`, the one list of the single player games of the browser, shared with web/; `web-shared/AGENTS.md`). `src/session/saves.ts` opens it once for the page; `src/session/savedGame.ts` has the slots and what localStorage keeps next to a game. A game of an address has a slot: `local.<seed>.<players>.<mask>` (`?local=…`), `scenario.<id>.<mask>` (`?scenario=…`); the page finds its game by the slot (`findSlot`). Every game of single player has the slot `single` and is found by its id (`?single=<id>`). An imported game of a fixed setup has an id only (`?save=<id>`). The writes go through the autosave of the store (300 ms after a save, at most 2 s, flushed when the page is hidden or left). A game of a table is kept from its first question on, so a reload of a started game is that game; a game of an address is kept from its first decision.
- **A game never fails to a blank page.** A render that throws shows the error, its stack and the components in place of the game, with Export and Start (`dev/GameCrash.tsx`, around every local game). The last error of a game (that render, an error of the page, an error of the engine) is kept next to it (`ti4.save.<id>.crash`), so its export carries it, also from the start screen when the page died.
- localStorage keeps, next to a game, what the page reads or writes at once: `ti4.save.<id>.cards` (the modes of the reactions), `ti4.save.<id>.wait` (the wait of a table, as the host set it last), `ti4.save.<id>.crash` (above), and `ti4.save.<id>.left`. A write of IndexedDB does not end when the page is left (a reload, a navigation): so when the page is left or hidden, it puts its newest save, with what the shown seat staged, into `ti4.save.<id>.left` at once, and removes it when the store has that save. The next page that opens the store (a game or the start screen) puts such a save into the store first (`takeLeft`), unless the store wrote the game after the page was left. Removing a game removes these keys.
- Export and Import are in the Dev sheet, and for every saved game on the start screen: Export in its row, Import in the header of the list. Export writes the export file of the store (`ti4-offline-game`, version 2, the same as web/'s), with `report` beside `game`: the browser (`device`) and the last error of the game in this browser (`crash`), for debugging; an import does not read it (`exportSave` in `session/saves.ts`). On a phone the file goes to the share sheet of the system, else it is a download (`dev/deliverFile.ts`). Import takes such a file as a new game with a new id: a game of a table is a game of single player (`?single=<id>`), another opens at `?save=<id>` (`importSave`). A file of an older version, or a game file of an older page, is refused with "The file is a saved game of an older version." The wait and the card modes are of this browser: an export does not have them.
- **Older saves are not read.** The keys of the pages before the store (`ti4.single`, `ti4.local.<…>`, formats 1 to 5 of the page) are removed at each start (`dropOldSaves` in `main.tsx`). A record of the store that does not validate (a save of format 1, a record of schema 1, web/'s saves of before) is counted (`status().unreadable`): the start screen says "1 saved game is of an older version. They cannot be played again." with "Delete". A game that another build of the engine saved may not play again (the game asks another question, or offers other options): the page says that the save is of another engine before it plays it.
- **The save list** is on the start screen (`/`, `src/dev/StartApp.tsx`, `StartScreen` of `src/game/lobby/`), under "Single player" and "Multiplayer": one row for each saved game, newest first. The row is the control and opens the game at its address; it says the kind ("Single player", "Local game · seed 3", "Scenario late-game", "Imported game"), the round and the phase, the seats, the factions of the seats played here and the answers, and when it was saved. "Export" writes its file; "Delete" opens a dialog that names the game; "Keep" leaves it. "Import" is in the header of the list, which is shown also with no game. The three are icons, with the name as the tooltip (AGENTS.md). A store that keeps the games in memory only (a private window, a newer database, a full disk) is said above the list and in the Dev sheet, with "⚠". The rows are made in `session/saves.ts` (`saveRows`). The list is of web2: web/ has its own over the same store.
- What a seat staged is kept by the engine, as the server keeps it online (owner, 2026-10-15; `ti4_host::staged`): the staged movement, landings and production with the number of their choice, the private draft of a tactical action and the draft of a secondary. Each seat of the page has its own; the page is told the slots of the seat that it is shown as (`Transport.staged`, `seatSync` over `put_staged` and `seat_staged`, as online). They are in the saved game (`staged`) and survive an undo and a redo; the save is written after each write. When the page is left (a reload, a tab that is put away) a write to the Worker would not come back, so the page puts what the shown seat staged since into the last save itself, and keeps that save in localStorage (`ti4.save.<id>.left`, below). After a reload the staged movement is staged again, so its systems keep their check marks.
- **The MLP models of a game** (`src/session/models.ts`). A game whose table seats a model (`mlp:<name>`) gets the file of each model before it starts: from the Cache API (store `ti4-models`, keyed by the address `/api/models/<sha256>.ti4m`, so a browser fetches a file once; it is checked against its SHA-256 before it is kept), else from the server. `LocalApp` hands copies of the bytes to the Worker as transferred buffers (`LocalPlay.models`, `engineLink`'s `models`), which loads them into each instance of the game before `ti4_host_start` (`ti4_model_load`) and refuses a file whose SHA-256 is not the one that `/api/models` lists. While a file loads the page says how far ("Loading Reviewer 473312 · 12 / 23 MB").
- **A saved game with a model** loads its models the same way before the engine plays it again. When a model cannot be had (no server, or the server no longer offers its name), the page says so in place of the game, with "New game" (the saved decisions would replay, but the game cannot go on). The save keeps the name, not the SHA-256: the game decides with the model that the name has now.
- The details, the measurements and the limits are in `crates/ti4-wasm/README.md`.
